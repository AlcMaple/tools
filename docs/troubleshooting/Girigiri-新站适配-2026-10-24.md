# Girigiri 新站适配与视频对照（2026-10-24）

## 结论与交付范围

Girigiri 的入口已经从旧 MacCMS 页面切成独立前端：旧路径仍可能回 HTTP 200，但内容只有挂载前端的 HTML 空壳。修复前，搜索因此误报 0 条、播放解析返回空标题/空线路/空集数，不是《死神》第 53 集没有更新。

本次仅修改网页版 Girigiri 数据适配及相关错误透传、回归脚本和文档。保留已有 `GV…` 绑定；生产部署和桌面安装包不在本次交付内。稀饭、媒体代理、播放器状态机与 10-12 的 Girigiri HLS 直连分支没有改动。

## 新旧页面与数据协议

| 功能 | 旧实现 | 本次确认的新协议 |
| --- | --- | --- |
| 搜索 | `/search/-------------/?wd=…`，解析 HTML，旧图片验证码 | 新界面 `/search?q=…`；`https://m3u8.girigirilove.com/api.php/Vod/get_list?vod_name=…&offset=0&limit=24` |
| 线路 / 选集 | `/playGV26595-1-53/`，解析 `player_aaaa`、tab 与播放链接 | `Vod/get_detail?vod_id=26595&user_id=`，读取 `info.vod_play_from`、`info.vod_play_url` |
| 源站外跳 | 旧 MacCMS 拼接路径 | `/play/26595?sourceIndex=0&episodeIndex=52`；两项都是新站过滤空条目后的零基索引 |
| 周表 | 向旧 `ds_api/weekday` 分七天请求，失败可能被吞成空表 | `App2/weekList` 一次返回七天；协议或 HTTP 错误直接呈现 |
| 既有绑定 | `GV26595` 等 | 保留 GV 编号，只在请求新 API 时取数字部分，不批量写库或猜另一部番 |

协议由用户指定的 Chrome 实际页面、新站公开 JS 的调用与真实 API 返回共同核对。新站仍公开提供返回旧版的链接，旧版当前在 `bg.girigirilove.com`；没有把旧版当成自动回退路径。

选集按标签解析真实集号，不按数组位置重编号。缺集返回 `LINE_EMPTY`；源站外跳缺集返回 `GIRIGIRI_EPISODE_NOT_FOUND`，不发一个会被源站悄悄改成第 1 集的 URL。PV / OVA 不冒充正片集号；单集电影的“正片”等标签对应第 1 集。

## 视频有没有变化

| 实测样本 | 当前旧版播放页与新版 API 对照 | 当前媒体信息 |
| --- | --- | --- |
| 死神 `GV26595` 第 53 集 | 两者 URL 完全相同：`https://ana.girigirilove.com/zijian/oldanime/2024/0607/Bleach/53.mp4` | MP4；193,596,019 字节，即 184.63 MiB，与用户截图的文件大小一致；时长 1476.01 秒；H.264 High、1440×1080、HE-AAC |
| 学生会也有洞！ `GV27203` 第 2 集繁中 | 两者 URL 完全相同：`https://akua.girigirilove.com/zijian/oldanime/2026/10/cht/SeitokainimoAnawaAruCHT/02/playlist.m3u8` | HLS；浏览器时长约 1420.10 秒；首段 ffprobe 为 H.264 High、1920×1080、HE-AAC |

两类媒体仍分 MP4 / HLS，没有改成新的签发、加密登录或播放协议。请求带 `Origin: https://anime.alcmaple.cn` 时，MP4、HLS 播放表和实取分片均返回允许该域的 CORS 头，因此保留 10-12 的 HLS 直连，而非重新绕回本站小带宽出口。

**与 10-12 文档的一个目录变化**：当时记录的“简中没有第 2 集”，现在已补出；新 API 两条线路均有第 1～3 集，Chrome 也实播了第 2 集简中线路。缺集仍需按每次实际列表判断，不固定记住历史缺集。

**对照边界**：以上比较的是“今天仍能访问的旧版播放页”与“新版 API”。历史文档没有保存 10-12 两个完整视频文件的哈希，因此只确认这些样本的媒体地址、格式、尺寸/文件大小等现状与已有证据相符，不声称全站媒体或历史文件逐字节相同，也不沿用 10-12 测速数字作为今天的性能结论。

## 代码与请求预算

- `web/server/girigiri/api.ts`：固定公开 API 地址、响应结构校验、2 MiB 响应上限、15 秒单次网络 deadline；不发本站会话或浏览器 cookie 给源站，不跟随 API 跨站重定向。
- 详情按番缓存 30 秒，并发请求单飞；换集、手动解析其它线路可复用同一份详情。周表缓存 6 小时，一次请求取七天。
- 搜索按 `offset/limit/total` 翻页，保留去重与页数上限；坏结构、提前结束、重复分页抛错，不伪装为“没有资源”。
- HTTP 429 / 5xx、业务 code、Cloudflare 拦截与传输异常分别保留原因；每次失败不自动重试、不周期探测，异常记录在服务端终端。
- 原验证码路由仅保留兼容入口，返回“新版搜索无需验证码”，不再请求旧验证码页。
- `web/server/girigiri/resolve.ts`、`search.ts`、`weekday.ts` 适配新数据；`web/server/girigiri.ts` 修正外跳，`web/server/player/index.ts` 透传 Girigiri 错误码。没有新增顶层 API 路由。

### 用户 Chrome 的本地实播

使用隔离临时数据和测试账号，服务仅监听 `127.0.0.1`，没有写线上账号、追番或绑定：

- 从追番卡片“继续看 → Girigiri”进入搜索，看到 15 项结果；点击《死神》保留第 53 集，完整显示 366 集和“简中”线路。
- MP4：元数据可用时 `paused=true`、时间为 0，等待用户手势；手动起播后连续推进到 67.7 秒。点击约 11:40 的进度位置后恢复推进到 12:03；没有解析错误。
- HLS：初始暂停、1920×1080、23:40；手动起播后推进超过 66 秒。跳到约 11:04 后恢复推进到 12:07；随后切到同集简中，线路选中态与实际播放一致。
- 服务端本次样本记录的跳转等待约 MP4 3.5 秒、HLS 4.5 秒；HLS 繁中一次短时测试的 QoS 为普通卡顿 0 次、1 次 seek 等待。这些只描述本次本地链路，不代表生产/iPhone 性能或整集不卡。
