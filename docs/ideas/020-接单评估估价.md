# 020 接单评估估价：RadQuote 调研与复刻方案

> 状态：调研完成，待审。审过后按下面「分阶段实现」逐阶段提交。

## 一、RadQuote 是怎么运作的（2026-10-23 读其前端代码实测）

首页「Try it now」是一个免登录试用区（他们叫 playground），前端只有一个 21 KB 的脚本，逻辑完整可读：

```
上传文件 / 选示例 → POST api.radquote.io/v1/playground/estimate   （multipart file 或 {template_id}）
                  ← { id, status, claim_token, summary? }
status 不是 done → 轮询 GET /v1/playground/estimate/:id
                    间隔 2s → 5s → 10s → 15s → 15s…（直到 done / error）
done  → summary { total, currency, hours, tasks, groups[...] }  → 渲染卡片
        可 POST /:id/email 发邮件（就是你收到的那封），claim_token 用来注册后认领这份估价
error → error_code 映射文案
```

**关键结论**

1. **没有「算法」可抄**。估价完全在他们服务器上由大模型做：从材料里抽出范围 → 拆成 WBS（任务组 → 任务 → 子任务，每个任务有若干 `estimates`，按角色给小时）→ 加总。页面上的「Development 650 / QA 237 / Integrations 196 …」就是按任务组把叶子任务小时求和。前端拿不到提示词、模型、费率卡。能复刻的是**这套输出结构 + 拆解方法**，小时数由我们自己的模型产出。
2. **「服务已满」是服务端限流，不是设备指纹**。截图里那句英文对应 `error_code: rate_limited`（前端文案键 `rateLimited`）。前端没有指纹、没有 localStorage 计数；请求带 `credentials: include`，所以限流依据只能是服务端的 IP / Cookie / 全局并发配额。「免费额度用完」和「人多」在它那里是**同一个 code**，所以分不出来——这正是我们 AGENTS.md 里禁止的那种文案合并。
3. **慢的原因**：异步任务 + 退避轮询，最快一档也要等到 15 s 一次的轮询窗口；模型本身做的是完整 WBS（示例里 Ecommerce 有 101 个任务）。
4. 它的内置示例给了量级参考：落地页 185 h / 33 任务，企业站 416 h / 40 任务，电商 2617 h / 101 任务。

## 二、我们怎么做

### 小时估算（替代 RadQuote）

- 复用现有接单评估的 AI 通道（`web/server/order-judge.ts` 的连接、默认服务器 AI / 用户自己的 key、桌面走网页账号），不新开一套。
- 一次调用，输出固定 JSON：`groups[{ name, tasks[{ title, hours }] }]`，组名用 RadQuote 那 8 类（需求与启动、UX/设计、开发、集成、QA 测试、部署上线、项目管理、培训与文档），服务端求和得总小时和各组小时，**不信模型自己报的总数**。
- 速度目标 20 s 内（最多 40 s）：
  - 不做异步轮询，直接 SSE 流式返回（带 `X-Accel-Buffering: no`），模型边出组边显示。
  - 关闭 thinking、任务粒度控制在 30~60 条叶子任务（RadQuote 的 101 条主要拖慢它）。
  - 估价可以和现有「能不能接」评估并行发出，不串行。
- 校准：拿你手上已有的 RadQuote 结果（如 1350 h 那单）做几组对照样本放进提示词当锚点；上线前用同一批材料对比两边的总小时，偏差写进日志。
- 失败按真实原因透出（AI 限流 / 额度 / 超时 / 材料读不出），不合并成一句「服务繁忙」。

### 价格（你的算法，纯本地计算，不经 AI）

```
低档小时 = ceil(总小时 × 0.06)      1350 → 81
高档小时 = ceil(总小时 × 0.075)     1350 → 102（101.25 向上取整）
低档工作日 = ceil(81 / 8) = 11      高档 = ceil(102 / 8) = 13
从「今天的下一天」起数工作日，跳过节假日、遇调休上班日照常算
  2026-10-22 下单 → 10-23 开工 → 第 11 个工作日 11-06，第 13 个 11-10
日历天数（含首尾）15 / 19 → 价格 15×160 = 2400 ~ 19×160 = 3040
加急：每提前 1 天 + (请的人数 + 1) × 160 × 天数
  请 1 人加急 1 天 +320；请 2 人加急 1 天 +480；请 2 人加急 2 天 +960
```

注：按日历天数计价意味着周末和假期也按天收费——与你给的例子一致，实现照此。

### 节假日数据

- 数据源：[NateScarlet/holiday-cn](https://github.com/NateScarlet/holiday-cn)，每年国务院发文后自动抓取，按年一个 JSON（`days[{date, isOffDay}]`，含调休上班日），jsDelivr 可直连。每年自动变，无需手维护。
- 服务端拉取后缓存到数据目录，按年存，一年一个文件；当年和下一年都取。
- **跨年还没发文怎么办**（实测今天 2027.json 是空的，`papers: []`；国务院通常 11 月发次年安排）：
  - 该年数据为空时按「只排双休」计算，结果标注「2027 年节假日未公布，按双休估算」——这是影响报价的状态，需要显示。
  - 元旦、春节必然落在年初，空数据时交期跨进那段的风险最大：额外提示「交期跨春节，实际可能顺延」。
  - 数据拉不到（断网）时用上次缓存；连缓存都没有就显式报错，不静默按双休算。
  - 不周期性探测：每次估价时若该年数据为空且距上次检查超过 1 天才重新拉一次。

## 四、已确认（2026-10-23）

1. 价格按日历天数（含周末假期）× 160。
2. 加急天数上限 = 该档日历天数（15~19 天的单最多加急 15~19 天）。
3. 跨年未公布按双休估算并标注。

## 五、修订：准确度先于速度

- **撤回「少拆任务」**：拆细是 RadQuote 准确的来源之一，不为速度牺牲粒度。提速改为按任务组**并行**生成（8 组同时发，墙钟时间≈最慢一组），粒度与 RadQuote 对齐。
- **上线闸门**：先做对照集——你提供约 10 单材料 + RadQuote 给的总小时 / 各组小时，我们的估算在同一批材料上跑；总小时、开发小时的中位偏差 ≤ 10%、单单最大偏差 ≤ 20% 才算「做得一样」，达不到不进阶段 3。
- **对照集**：先用你的 2 单（语音会议 1350 h / 开发 650；多链钱包两次生成 1920 h / 开发 880 和 2007 h / 开发 782），之后每单两边各跑一次持续追加。RadQuote 自带 3 个示例（`radquote.io/playground/` 可下载，185 / 416 / 2617 h）作为补充。
- **误差口径**：不要求一模一样——RadQuote 自己同一份需求两次就差：总小时 +4.5%，开发 −11%，QA +38%。所以：
  - 只比**总小时**和**开发小时**，其余组 RadQuote 自己都摆动很大，不作指标。
  - 指标 = |我们 − RadQuote| / RadQuote；RadQuote 跑过多次的取平均。总小时 ≤ 10%（约它自身波动的 2 倍）、开发小时 ≤ 15% 算达标。
  - 落到报价上看「工作日差几天」：1920 vs 2007 h → 低档 15 vs 16 天、高档 18 vs 19 天，10% 的小时差约等于 1~2 个工作日，这是用户真正感知的误差。
  - 我们自己同一份需求跑 3 次，波动不能大于 RadQuote 的。
- RadQuote 不理会需求里的工期要求（「7 天内完工」照样给 1350 h），我们的小时估算同样只估工作量；工期要求意味着加急，由用户按页面说明自己算加急费。
- 价格默认显示不加急；加急只在页面上写计算方法，不做输入控件。
- **备选路线**：RadQuote 有官方 API / MCP（Plus $79/月，50 次生成；MCP 仍是预发布、只有 stage 环境，且官方流程每 15 s 轮询一次），速度和次数都达不到要求，只作为对照集达不到时的退路。
- **入口**：评估页一个按钮同时发「评估」和「估价」两个请求，结果分两块显示、各自失败互不影响，不合并成一次 AI 调用（两份输出结构不同，合并会让一方的失败或截断拖垮另一方）。
  - 实现时改为**一个请求、一个 AI 回合里并行两组调用**：服务器 AI 每人同时只能占一个回合，两个请求会互相顶掉（`RUN_BUSY`）。仍是两块结果、各自失败互不影响，AI 调用也仍然分开。
