## 第一版如何接入

1. **在作品详情里按需查找。** 沿用目录已有的访问权限、Bangumi ID、别名、播出日期和集数。优先查 AnimeGarden 的公开 HTTP API，ID 查询成功且结果为空时再查名称，结合季度、TV／剧场版和文件表判断。覆盖该季全部正片才标为整季，部分分集包如实写「第 1–6 集」，文件表截断或范围存疑时保留原标题。同一 BT 发布跨站按种子哈希去重，保留来源。上游返回 429 或 5xx 就结束本次查询，显示对应原因，保留已有缓存和管理员链接。[目录详情代码](../../web/server/bgm/catalog.ts#L170) · [AnimeGarden 接口示例](https://github.com/yjl9903/AnimeGarden/blob/main/examples/api.http)
2. **同时给出整季和单集的可用方式。** 有现成 ZIP 或视频直链就交给浏览器，已安装的兼容下载扩展可接管。跨站 MP4 要核对最终响应是否声明附件，否则浏览器可能打开播放器。磁力提供「打开下载器」和「复制磁力」，有种子文件时也可保存。用户可在 Windows 的 qBittorrent 或 macOS 的 Transmission 里勾选具体文件。只有磁力合集时仍列出可直下的单集。稀饭和 Girigiri 的既有解析可补充候选，实际要区分可下载的媒体文件、HLS 播放列表和临时地址。[HTML 下载规范](https://html.spec.whatwg.org/multipage/links.html#downloading-resources) · [qBittorrent](https://www.qbittorrent.org/) · [Transmission](https://transmissionbt.com/download) · [稀饭](../../web/server/xifan/resolve.ts) · [Girigiri](../../web/server/girigiri/resolve.ts)
3. **管理员直接维护作品的下载链接。** 沿用目录的管理员校验，支持新增、修改、移除。每条记录保存对应作品、覆盖集数、链接类型和可选的字幕／清晰度。区分文件直链、磁力、种子文件和发布页，让按钮执行对应动作。手工记录随站点运营数据备份，独立于每周重建的索引，自动搜索刷新时保留。发现坏链可以替换原记录，上游暂时不可用也能展示手工补充。[目录管理入口](../../web/server/index.ts#L219) · [现有目录覆写数据](../../web/server/bgm/catalog.ts#L48)
4. **本站托管的文件复用备份页的下载交互。** 登录后提前取票，实际点击普通链接，兼容丢失 Cookie 的下载扩展。视频票据用途独立，绑定文件和版本。现有备份票有效 120 秒，图片有 200 MiB 上限，ZIP 由 `zipSync` 一次性装入内存。大文件用短票换取在下载会话内有效的地址，同一下载器的 HEAD、分段 GET 和续传都可重复读取该版本。对需要由本站合并的完整分集，先流式写入带 CRC 的 ZIP64 成品，视频原样存储，完成校验后再发链接。这样下载中途断线能重新读取同一份文件。[备份页链接](../../web/src/BackupModule.tsx#L117) · [现有票据](../../web/server/backup.ts#L201) · [现有打包方式](../../web/server/backup.ts#L292) · [Archiver 的 STORE 与 ZIP64 支持](https://www.archiverjs.com/docs/archiver/)

AnimeGarden 的客户端包在所查版本声明 Node ≥24、AGPL-3.0，本站网页版声明 Node ≥20。首版直接调用公开 HTTP 接口即可。ANi 的目录遍历可参考 AutoFilm，按目标作品或季度补历史，比每次打开详情都重扫目录合适。[客户端清单](https://github.com/yjl9903/AnimeGarden/blob/main/packages/client/package.json) · [网页版运行要求](../../web/package.json#L6) · [AutoFilm 源配置](https://github.com/AkimioJR/AutoFilm/blob/main/src/ani2alist/config.rs)

## 冷门磁力怎样还能下载

磁力里的哈希用于验证内容。即使完整做种数显示为零，只要能连接的各方合起来仍有全部分片，或者有对应版本的 HTTP 镜像，就有机会下完。如果所有来源都缺同一块，换解析器也补不出那一块。迅雷公开披露过同时从用户节点和服务器寻找同一文件的机制，这可以解释一部分看似无种的下载。单次任务究竟命中哪个来源，外部无法判断。[BitTorrent 元数据协议](https://www.bittorrent.org/beps/bep_0009.html) · [WebSeed 协议](https://www.bittorrent.org/beps/bep_0019.html) · [迅雷公开披露](https://ir.xunlei.com/static-files/a6202233-d300-4ccf-8353-fd30b0ab4168)

用开放动画《Sintel》做了一个可复核的小实验。按 WebTorrent 官方示例从 HTTPS 取种子，核对磁力哈希，再从种子登记的 HTTP 镜像读取编号 1 的分片。取回 131,072 字节，SHA-1 与种子内该片的记录一致，全程没有连接 BT 节点。这个办法依赖镜像事先保存同一版本的文件。普通网页内的 WebTorrent 还受 WebRTC 节点兼容性约束。[官方示例](https://github.com/webtorrent/webtorrent/blob/master/docs/api.md) · [WebTorrent 浏览器限制](https://webtorrent.io/faq)

如果希望**只有磁力也能在浏览器下载**，可试自托管 Webtor。它已有逐文件 HTTP 下载、整包下载和 Vault 保留副本的实现。有源时先取齐并校验，可长期分发的冷门合集放入持久存储，之后用户直接从副本下载。首次入库仍需有人或镜像能提供全部数据，后续速度受本站存储、出口和用户线路约束。公共 Webtor 的带宽与账号档位有关，官方也提示其即时 ZIP 在部分解压工具中可能触发 CRC 警告。[Webtor 自托管仓库](https://github.com/webtor-io/self-hosted) · [公共服务的速度与 ZIP 说明](https://webtor.io/torrent-to-zip)

## 实施顺序与验收

首版交付资源查找、管理员补链、浏览器直链和系统下载器。第二阶段用可再分发的样本验证自托管下载与成品 ZIP，再根据实际磁盘占用和出口流量决定长期保存哪些合集

- 在 Windows 和 macOS 分别验浏览器原生下载、已安装的下载扩展，以及已关联和未关联磁力协议的情况
- 用已知完整合集、同名续季、含电影或音乐的混合包、仅有单集、上游限流五类样本核对展示。管理员改链后刷新目录和重建索引都应保留改动
- 对自产 ZIP 使用超过 4 GiB 的合成文件组，分别用 Windows 资源管理器和 macOS 归档实用工具解压并校验内容。暂停到取票有效期之后再续传，核对同版本文件、分段响应和最终哈希
- 对自托管候选分别验证有源冷启动、上游离线后命中已存副本、首次获取就缺片。记录首字节时间、完成时间、磁盘峰值和实际出口字节。当前实测覆盖索引与 HTTP 分片，自托管性能、整季传输和双平台客户端体验留待实施验收
