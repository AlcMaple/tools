# 013 - 邮箱验证码注册与登录

> 2026-10-06 收口：验证码基础已落地。只保留当前身份规则和维护边界；[早期论证](archive/013-邮箱快捷注册与登录-原方案.md)不再日常加载，第三方配置见 [015](015-noreply发信与第三方登录接入指南.md)。

## 保留结论

- 邮箱入口是“输入邮箱 → 一次性验证码 → 登录/建号”，不是读取浏览器里已填的邮箱直接免验证。浏览器自动填充、收件箱直达和设备指纹都不是邮箱所有权证明。
- 新邮箱验证后可建无密码账号；有效本站会话免重复收码，退出、换设备或会话失效后重新验证。旧账号兼容不能因新增入口被默默删除。
- 验证码只存 HMAC，单次、过期、错误次数、发送/校验限流和重发作废旧码均要保留；不要把历史具体阈值当成永不变化的配置。
- 本轮核对 `web/server/oauth.ts`：Google/GitHub 按已核验邮箱进入本站账号，Google 的旧“永远按 sub 绑定”叙述已过时；Linux DO 是另一路提供方身份绑定。不要用一套并号逻辑概括所有提供方。
- 密码、换邮箱、绑定/解绑和无密码账号各有前置条件；避免用户移除最后一种可用登录方式。错误应区分本站凭据、上游授权、邮件投递和限流。
- 本站账号与稀饭账号是两套认证；在浏览器登录源站不等于服务端获得该用户的源站会话。

## 维护与验收

- SMTP 未就绪不应把所有登录方式一起停用；开发 console 模式不代表真实发信。密钥放部署目录外，不进日志、仓库或同步数据。
- 第三方按钮仅在实际配置可用时显示；state/nonce/PKCE、回调有效期和目标校验按各自协议执行，外部回跳不变成任意 URL 跳转。
- 邮件与真实 OAuth 的当前线上可用性本轮未测；特别是 09-12 GitHub 日志只记录隔离测试，没有真实授权完成证据。部署、账号迁移或凭据轮换后再做端到端。
- 代码入口：`web/server/auth.ts`、`oauth.ts`、`email-delivery.ts`、`web/src/AuthModal.tsx`。这是文档归纳，不新增登录功能或承诺新提供方。
