# 013 - 邮箱验证码注册与登录

> 开始：2026-08-08
> 最近复核：2026-08-15

## 结论

1. 浏览器自动填充、密码管理器保存的邮箱只是输入便利，不能证明用户当前控制这个邮箱；因此不能拿「浏览器里已经有邮箱」跳过首次验证。
2. 邮箱入口统一采用「一次性验证码」：已存在且已验证的邮箱直接登录；新邮箱验证后自动生成用户名、创建无密码账号并登录。验证码单次、10 分钟过期、最多 5 次错误、按 IP / 邮箱限流，重发后旧验证码失效。
3. 当前 30 天 `HttpOnly` 会话已经提供安全的「后续不用验证码」：只要同一浏览器的会话仍有效就保持登录；主动退出、换设备或 Cookie 失效后必须再次验证。不能用设备指纹代替邮箱所有权证明。
4. 旧用户名 / 密码账号不迁移、不停用；新邮箱账号显式记录为无密码账号，普通密码登录、设置和找回接口都识别该状态。这样不会为了新流程让已有用户依赖 SMTP，也不会给无密码账号展示永远无法通过的「原始密码」表单。
5. Google、Microsoft 等真正的一键登录属于 OIDC 联邦身份：需要平台注册的 Client ID、回调地址和服务端令牌校验，并以 `provider + subject` 作为身份键。QQ 同样需要平台应用接入；没有确认到可供本站直接使用的 163 个人身份 OIDC 能力。它们不能用「浏览器里正登录该邮箱」冒充。
6. 本次不会把邮箱自动绑定到已有的用户名账号。已有邮箱凭据的账号可以验证码登录，旧用户名账号继续使用原登录方式；如需绑定，应另做「已登录账号 + 再验证邮箱」的显式流程，避免误合并账号。

## 数据与流程

```text
邮箱 ── start ──→ email_challenge（HMAC(code)、10 min、attempts）
  │                         │
  │                         └─ verify ──┬─ 已有 email → 签发本站会话
  │                                    └─ 新 email → 自动建无密码账号 → 签发本站会话
  └──────────────────────────────────────── 退出 / 换设备 / 会话失效后重新收码
```

验证码邮件通过 SMTP 发送。开发环境默认只在服务端控制台输出验证码；生产必须设置 `EMAIL_MODE=smtp`、`SMTP_HOST`、`SMTP_FROM` 等环境变量，缺失时只停用邮箱入口，不影响原有账号体系。

## 常见产品为什么看起来「不用验证码」

- **第三方授权登录**：Google / Microsoft 等身份提供方已经在自己的页面完成密码、Passkey 或风控验证，本站拿到的是经过签名的 OIDC 身份声明，不是读取浏览器里的邮箱字符串。本站仍必须校验签名、`iss`、`aud`、`exp`、`state` / `nonce` 等边界。
- **仍在登录会话里**：用户以前已经验证过，浏览器继续携带安全会话 Cookie，所以页面直接进入；这不是永远跳过验证。会话退出、过期或换设备后仍要重新认证。
- **Passkey**：浏览器和系统用站点绑定的公私钥完成无密码认证，私钥不交给网站，比邮箱验证码更抗钓鱼。它适合未来作为真正的免验证码入口，但不能用设备指纹仿造。
- **邮箱验证码 / Magic Link**：实现最轻，但安全上依赖邮箱账户本身和邮件链路，适合当前站点的低风险账号入口，不应宣称为强 MFA。
