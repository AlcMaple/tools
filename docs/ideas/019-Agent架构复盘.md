# 019 Agent 助手架构复盘

问题：「一个 bug 衍生一堆 bug，是不是方向错了？」
结论：**方向没错，架构不是病灶；病灶在验证层。** 下面是证据，不是判断。

## 一、架构对照业界形态

阶段 1–8 落成的动作模型：

```
模型只能提案 → 用户点击确认 → 服务端执行 → 权威回读/回执 → 状态机推进
```

这正是当前主流做法（Bedrock Agents 的 user-confirmation、plan-then-execute 论文里的
「计划与执行分离」）：读操作直通、写操作闸门、破坏性操作不进工具集；步数/时长/token/
调用数各有显式预算，超了停下来。`permitsActionTransition` 还多做了一层多数实现没有的事 ——
**证据按来源分级**（server / user_click / browser / player，`model` 一律拒绝），
所以模型自称「已经播了」永远推不动状态机。这不是自创的怪东西，是同一形态的严格版。

## 二、依赖结构实测

`server/agent/*.ts` 27 个模块的内部 import 图：

- **无运行时环。**唯一一条回边 `knowledge → site-features → knowledge` 是
  `import type { FeatureDescription }`，类型级，编译后消失。
- **纯叶子承担规则。**`policy`（fan-in 13）、`validation`（fan-in 14）零依赖，
  全是纯函数。状态机、预算、配额、价格都在这里 —— 可以单测到底，也确实被测到了。
- **fan-out 最高的 `run-runtime`（10）只有 50 行**，是组装根（把 store / tools / provider 接起来），
  不是上帝对象。

分层是干净的，没有找到「改一处塌一片」的耦合。

## 三、那这一轮的 bug 从哪来

| bug | 类别 | 测试为什么没抓到 |
|---|---|---|
| 估算器按字节数当 token | 纯函数的**量纲**错 | 断言了形状，没断言数量级 |
| 终端 SSE 帧漏 `actions` | 服务端帧与客户端类型**契约漂移** | 两侧各自测，没有一个测跨过边界 |
| ui 夹具硬编码 6 个工具 | 夹具**抄了一份生产真相** | 夹具错了，测试照样绿 |
| 共享连接绑在首个调用者的 signal | **生命周期**错 | 无用例覆盖「发起者中途离开」 |
| C11 等一个不会再发生的拒绝 | 测试**自身**挂起 | 套件只数「跑过几条」，不数「该跑几条」 |

五个里没有一个来自架构耦合。**全部是「测试无法察觉的那一类错误」。**
所以修 bug 会衍生 bug 的感觉是真的 —— 但成因不是设计错，是每次改动之后
没有任何机制能告诉你「这次少验了什么」。最后一条尤其致命：它让前四条的回归
**看起来**是绿的。

## 四、反循环机制

`scripts/agent-fixtures.ts` 的 `checkPlan(prefix, planned, progress)`：

- 套件声明**计划条数**，收尾时与实跑数比对，对不上以 1 退出；
- 带看门狗，挂起时不再落到含义模糊的 exit 13，而是打印「停在第几条」再退出 1。

已接入 12 个套件（CT45 / H30 / CX29 / R38 / T16 / P19 / D33 / S11 / X11 / U50 / E36 / C17）。
接入当天就抓到一条：`test-agent-sources` 实跑 11 条，而汇报 JSON 长期只显示 1。

下一步优先级（按上表的类别，不按 bug 数）：
1. 契约漂移 —— 服务端帧与客户端类型由 `shared/` 单一来源生成或互测；
2. 夹具复制 —— 剩余夹具一律 import 生产常量（`agent-ui-fixture` 已改）；
3. 量纲 —— 估算类纯函数补数量级断言（真实语料 ±30%）。

## 五、教训

- `cmd | grep` 返回的是 grep 的退出码。多轮「全绿」汇报因此漏报了一个一直失败的套件。
  验证只读 `$?`。
- 一个不会失败的测试比没有测试更坏：它把「没验」伪装成「验过了」。
