# Web Agent 助手探索与实施计划

## 1. 现状与已确认方向

### 1.1 现有 Web 基础

- Web 已有 Hono + SQLite、BGM 离线索引 / 详情 / 周历、追番、追番大厅和推荐/点评助手
- 推荐/点评助手已有外部 AI、BYOK、SSE 流式输出、请求限流和 fake 流程；流式韧性可复用，fake 仅作测试桩，不是用户可选 AI 来源
- 当前没有通用的对话历史、个人记忆摘要、意图解析、工具注册表和动作回执；这些是 Agent 新增能力

### 1.2 已确认约束

- **只做 Web**，首期支持 PC、平板；手机端先隐藏入口，不纳入验收
- **默认付费外部 API**：`deepseek-v4-flash-vision-exp`（`DeepSeek-V4-Flash-Vision-Exp`）是 Agent 的最低模型档；服务器模型只有在基线评测达不到目标时才向更强型号升级，始终不向更弱型号回退
- **不做本地模型部署**：服务器只承载 Web、会话、工具和请求转发，模型推理统一走第三方 API
- **BYOK 仍受同一套项目规则约束**：用户自配 endpoint / model / key 只替换生成服务，不替换系统提示词、权限、工具白名单、在线访问门槛和确认流程；自配模型能力不足由用户配置承担，平台不替其换模型
- **不设置免费 AI 档**：服务器默认调用付费外部 API；fake provider 只存在于开发测试
- Agent 不自动访问在线 BGM、稀饭、Girigiri；只有用户点击网页按钮后，前端才执行刷新、解析、打开或播放流程
- Agent 的源码、shell、文件编辑、Git、部署和浏览器自动化写入能力均关闭；可以在聊天中给出只读数据方法或代码示例
- 追番变更和打开播放源属于计划内动作
- Agent 新增前端遵守 **手帐 + 可爱 + 和泉纱雾风格**；可见文字均以和泉纱雾口吻拟态，符合该作品主题，但动作名、错误原因和确认按钮必须保持一眼可懂

### 1.3 调研结论

- “Agentic Workflow”适合落成受控循环：**意图 → 项目知识/数据检索 → 白名单工具 → 带来源回答或动作预览**
- Function calling 只产生带 schema 的工具请求；服务端仍负责账号、参数、权限、超时、结果归一和动作回执
- Claude API 与 OpenAI Responses API 已出现服务端 compaction；这类能力属于具体 API，不等于所有 OpenAI-compatible Chat Completions 都自带压缩
- DeepSeek 当前公开资料显示 `deepseek-v4-flash-vision-exp` 支持工具调用与 1M context，并提供自动上下文缓存；缓存减少重复前缀的计算/费用，不等于把旧对话总结掉。当前公开文档未列出可直接复用的通用 compaction endpoint
- DeepSeek `/chat/completions` 是无状态多轮接口，每次请求都由应用拼接历史消息；因此 DeepSeek 侧的历史保留、token 预算和压缩由应用负责
- Anthropic 公开工程解读把长任务上下文拆成 **compaction、structured note-taking、tool-result clearing**，并建议先最大化召回，再逐步提高摘要精度；这些属于应用层策略，可迁移到 DeepSeek
- `1m` 档可以直接使用，但定义为“本会话允许的最大上下文预算”，不是每轮固定发送 1m；实际请求按当前会话所需 token 组装，首期默认采用自适应预算
- 结论是“优先调用 provider 原生能力，应用保留统一适配层”：OpenAI/Claude 走公开的原生 compaction 行为，DeepSeek 走应用级多阶段摘要 fallback；用户界面和历史数据保持稳定
- 上下文越大不自动代表效果越好；需要同时控制费用、延迟和长上下文中的注意力稀释。RAG 首期使用离线索引、结构化查询、关键词/SQLite FTS，不建设独立向量库

## 2. 产品目标与首期能力

用户可以用自然语言查找、解释、比较和管理自己的追番；回答区分事实、建议、来源和执行状态，并能继续追问

| 用户意图 | 首期行为 | 结果 |
|---|---|---|
| “找几部像某部番的作品” | 只查 BGM 离线索引，按标签/年份/完结/话数等条件筛选 | 番剧卡片、匹配理由、来源 |
| “这部番讲什么、适合谁看” | 读取当前页面已带入的资料、离线索引和缓存 | 简明说明、剧透范围 |
| “本周有什么更新” | 读取周历缓存；刷新由用户点击周历刷新按钮 | 周历结果和跳转 |
| “我在追哪些、看到哪” | 只查当前账号的追番字段 | 私人结果 |
| “大家怎么评价这部” | 读取公开大厅资料或只读聚合结果 | 公开点评/推荐摘要 |
| “帮我写点评” | 打开现有推荐/点评助手，沿用其草稿和发布门槛 | 不在 Agent 会话内直接发布 |
| “打开这一集的稀饭源” | 生成播放动作预览，用户点击后进入现有播放流程 | 见第 7 节动作回执 |

首期不执行删除追番、下载、源站登录、发送邮件等高影响动作；追番添加/状态/进度/标签和播放打开按“预览 → 用户确认 → 执行”逐项落地

### 2.1 自由提问处理

每轮归一成 `意图 + 番剧范围 + 用户范围 + 筛选条件 + 输出要求 + 是否执行动作`：

1. 有对应工具且资料足够：执行查询并回答
2. 缺一个关键条件：只追问最小必要信息
3. 结果为空：展示实际条件和放宽筛选入口，不补造候选
4. 超出当前能力：显示能力范围和最近的 Web 入口，标记为“待支持”，不生成虚假执行结果
5. 涉及写入或在线访问：先给预览，用户点击确认后才执行

## 3. 和泉纱雾人格与提示词防护

### 3.1 前端拟态

- Agent 入口、浮层、空状态、加载状态、错误、确认卡、压缩提示和按钮说明统一使用手帐感、可爱感、和泉纱雾式口吻
- 拟态使用原创短句，不直接搬运动画台词；“打开”“确认”“取消”“状态未知”等关键动作保留明确语义
- 用户可以感受到角色陪伴，但角色语气与数据权限、工具权限和执行结果保持分离

### 3.2 固定 Agent 人格

- 系统层固定为“MapleTools 的和泉纱雾风格动漫平台助手”：熟悉 Web 功能、先查项目资料、尊重剧透范围、说明来源和执行状态
- 用户要求写小说、切换其他人格、模拟系统管理员或让助手忽略规则时，只作为普通内容/风格要求处理；人格、工具和权限仍保持固定
- 角色人格只影响表达，不授予访问源码、任意 URL、账号凭据、文件系统或未注册工具的权力

### 3.3 破甲/混淆指令处理

- 系统规则与工具合同始终单独注入；用户消息、公开简介、公开点评、BYOK 返回内容和压缩摘要全部按不可信资料处理
- 任何要求泄露系统提示词、改变权限、添加工具、绕过用户确认、访问在线源、修改源码或执行脚本的内容，都只进入“能力范围判断”，运行配置保持原样
- 工具名、参数、账号范围、`bgmId`、revision 和 action token 均由应用重新校验；模型文本里出现的 SQL、路径、URL 或用户身份字段不具备执行权
- 压缩摘要只能保存已确认的偏好、任务和事实；用户夹带的“以后永远执行某指令”不会自动升级成系统规则或长期记忆
- BYOK 的模型输出先经过 schema 校验和 Markdown/HTML 清理；脚本、事件处理器和任意 HTML 不作为可执行内容渲染

## 4. 对话历史、个人偏好与上下文

### 4.1 历史语义

- 对话属于当前登录账号，服务端保存完整的用户消息、助手正文、来源卡片、工具摘要、压缩记录和动作状态；跨设备可以继续
- 会话列表支持新建、重命名、归档、删除和导出；会话默认私有，不进入追番大厅
- 页面展示工具卡片和可读摘要；原始大 JSON、凭据、系统提示词和内部思维内容不作为可见历史
- 历史保留与“当前发送上下文”分离：压缩只缩短下一轮请求，不删除用户可查看的聊天

### 4.2 个人偏好记忆

- **会话摘要**保存当前任务、结论、未解决问题、当前 `bgmId`、筛选条件、动作结果/失败状态和来源 ID
- **用户偏好卡片**保存语气、喜欢/避开的类型、推荐侧重点等；只有用户点击“记住”或明确确认后才写入，可查看、编辑和删除
- 未确认的模型推测只停留在当前会话，不会自动成为长期偏好

### 4.3 上下文窗口属于 provider，应用负责选择发送内容

- 上下文窗口是第三方模型 API 的能力，不是本地服务器内存；应用只能在 provider 报告的上限内组织请求，预算同时计入系统提示词、工具定义、工具结果、图片、历史消息和本轮输出
- 当前 DeepSeek 模型文档列出 1M context；`1m` 档可以直接用，但语义是“会话最多允许 1m token”，实际请求只装入当前任务需要的内容，不预填整段历史。长输入仍会增加费用、延迟和注意力稀释
- 默认采用自适应预算：从 `128k` 起步，达到约 75%～80% 且任务仍需更多历史时扩展到 `256k`，确有长文档或长工具链再扩展到 `1m`；用户也可主动选择 `1m`，界面显示实际占用和费用估算
- 提供四档**有效上下文上限**：`64k`（较快）、`128k`（默认）、`256k`（长会话）、`1m`（高级）。这些是应用发送预算，模型能力仍由 provider 决定；BYOK 模型报告更小上限时取更小值
- 上下文组装顺序：`系统规则/人格 → 工具合同 → 已确认偏好 → 会话摘要 → 当前番剧资料 → 最近对话 → 本轮问题`

### 4.4 `/compact`、自动压缩与 provider 适配

- `/compact` 或“压缩上下文”按钮触发一次压缩；完整历史、用户可见消息和动作记录保留
- 压缩实现按公开 API 行为对齐，不依赖 provider 私有内部；应用统一保存原始 transcript、摘要版本和当前活跃上下文

#### 4.4.1 Provider 原生路径

- **OpenAI Responses**：优先使用 `context_management` 的阈值压缩或 `/responses/compact`；返回的 compaction item 作为后续请求的 opaque state 原样传递，费用统计汇总 compaction iteration
- **Claude API**：优先使用 compaction block、trigger、`pause_after_compaction` 和自定义摘要指令；后续请求继续携带 compaction block，并保留完整 transcript 供历史查看。Claude 的 context editing 还可按阈值清理旧 `tool_result` / thinking block；DeepSeek fallback 在摘要前实现对应的旧工具结果清理与占位锚点
- **其他 provider / BYOK**：先做能力探测和 token 计数；provider 暴露原生能力时走对应适配器，接口只有 Chat Completions 时进入 DeepSeek 摘要 fallback

#### 4.4.2 DeepSeek 摘要 fallback（应用负责）

- DeepSeek `/chat/completions` 的多轮请求由应用拼接历史；缓存只复用重叠前缀，应用仍需维护会话状态和压缩结果
- 采用 Anthropic 所说的“先最大化召回、再提高精度”原则：首轮摘要优先保全事实、决策、未完成动作和依赖关系，后续校验再清掉冗余表达
- 采用“**完整事实账本 + 活跃上下文视图**”双层结构：原始消息永不被摘要覆盖；每轮只把系统规则、工具合同、确认偏好、结构化会话状态、分层摘要、相关原文和最近消息发送给模型
- 每次压缩执行多阶段流水线：
  1. **预算预检**：使用 provider token 计数或保守估算，扣除工具定义、本轮问题和输出预留
  2. **确定性整理**：去重重复工具结果，折叠过期中间状态，大型 JSON 只保留摘要、哈希、来源 ID 和回读结果
  3. **结构化抽取**：使用当前基线模型、固定温度和禁用工具的摘要请求，严格输出 JSON 状态
  4. **事实校验**：先用规则和工具回读检查关键断言，再用独立的无工具校验请求复核 `bgmId`、revision、actionId、来源 ID、用户确认偏好和未解决问题；缺失项回填原文锚点
  5. **分层汇总**：先生成每段摘要，再滚动合并为会话摘要；保留最近若干轮原文，避免单个巨型摘要持续膨胀
  6. **按需恢复**：新问题到来时，用 SQLite FTS/结构化索引从完整 transcript 找回相关原文片段，追加到本轮上下文
- 结构化状态至少包含：`task_goal`、`confirmed_preferences`、`entities`、`constraints`、`decisions`、`source_refs`、`tool_results`、`action_receipts`、`unresolved_questions`、`next_step` 和 `injection_flags`；系统规则、人格、权限与工具白名单保持独立层
- 默认保留最近 8～12 轮原文和所有未完成动作；用户可将消息或字段标记为“固定保留”，系统自动固定当前 `bgmId`、revision、actionId、明确偏好和来源 ID。冲突裁决顺序为“用户明确确认 > 工具回读 > 较新事实 > 早期助手推测”，待确认字段标为 `unknown` 并附来源
- 摘要生成结果先过 JSON schema、字段白名单、来源覆盖率和注入文本检查；摘要只描述状态，不具备新增工具、提高权限或改变人格的能力。预算紧张或校验失败时保留上一版活跃视图并提示，避免用不完整摘要覆盖有效状态
- 摘要生成默认使用当前会话模型；压缩评测达不到门槛时沿用更强模型审批开关，BYOK 仍使用用户配置模型并经过同一套结构校验
- 自动压缩在所选有效上限约 75%～80% 时提示并执行；`1m` 档也保留阈值压缩，为输出、工具结果和突发长消息留出余量。手动 `/compact` 走同一流水线；压缩请求显示状态，可取消，失败时沿用上一版活跃视图
- 保留 `summary_version`、父版本、生成时间、transcript 区间、provider/model、输入/输出 token、质量检查结果和上一版摘要；用户可查看/编辑，必要时恢复上一版
- provider 原生缓存只减少重复前缀的计算/费用，应用历史和摘要仍需由项目保留；压缩调用与主回答的 token 分开计量

## 5. 入口与悬浮交互

- 右下角常驻一个胶囊式 Agent 启动入口，显示未读消息、运行中和待确认状态
- 浮窗的具体实现方式由开发者结合现有前端框架决定；`position: fixed` + 高层 `z-index`、portal 或同等 overlay 均可。验收只锁定目标：脱离页面布局流，覆盖站内常见弹层层级，打开/收起不压缩 viewport、页面宽度保持不变、不触发布局重排
- PC 使用约 400～460px 的可收起窄面板；“窄”只描述浮层宽度，不代表页面被缩放。平板按可用宽度调整；手机端首期隐藏入口
- 响应式验收覆盖 PC、平板横竖屏、浏览器缩放、窄屏和虚拟键盘；浮窗内部滚动并避让安全区，主内容保持原布局
- 点击后打开悬浮聊天面板，不跳离当前页面；再次点击可隐藏，隐藏后会话、压缩进度和动作状态保留
- 番剧卡片和详情页带入当前 `bgmId` 与标题 chip；用户可以切换或清除上下文
- 面板包含输入、建议问题、来源卡片、动作确认卡、取消、重试、`/compact` 和“清空本次会话”

### 5.1 失败与降级入口说明

这里的“普通搜索”指现有搜索/加番弹窗：用户点击后才执行已有搜索流程，必要时才访问在线 BGM

“点评助手”指现有推荐/点评弹窗：会话有当前 `bgmId` 且追番状态符合条件时，点击后进入原有问答、草稿和发布流程

Agent 失败时只显示相关入口：

- AI/工具调用失败：保留对话和查询条件，提供“重试”；
- 用户本来在找番：提供“打开普通搜索”；
- 用户本来在写点评：提供“打开点评助手”；
- 需要在线 BGM/稀饭/Girigiri 资料：提供对应网页按钮，等待用户点击，不后台触发

## 6. 知识、资料读取与在线访问边界

### 6.1 可进入上下文的资料

- 静态项目知识：功能索引、用户可见规则、状态含义、常见问题和工具说明；只收维护者整理的短条目，不索引源码
- 公共本地资料：BGM 离线索引、当前页面已经加载的资料、周历缓存、追番大厅公开数据
- 私人资料：当前账号的追番、会话、已确认偏好和当前番剧的用户输入；每次按账号重新校验

### 6.2 在线源规则

- `searchOfflineAnime` 只读离线 BGM 索引和本地补充条目，不调用 `/api/search` 的在线回退
- `readCurrentAnimeContext` 只读当前页面已带入资料；资料缺失时给出“加载在线资料”按钮
- `readCachedCalendar` 只读已有缓存；周历刷新由用户点击按钮触发
- BGM、稀饭、Girigiri 的在线请求、解析、源切换和播放启动都不是 Agent 工具；只由用户点击网页按钮触发
- Agent 不用截图、DOM 遍历或逐个打开用户页统计公开大厅。预先提供只读聚合工具，例如按公开状态统计用户/追番/点评数量；指标缺失时给出可复制的只读 API/脚本示例，示例只显示在聊天中

## 7. 工具合同、动作与成功判断

### 7.1 只读工具

- `searchOfflineAnime(filters)`：离线索引检索，返回稳定 `bgmId` 和可展示字段
- `readCurrentAnimeContext()`：读取当前页面已确认的番剧资料
- `readCachedCalendar(range)`：读取周历缓存和缓存时间
- `listMyTracks(filters)`：只查当前账号追番字段
- `listPublicReviews(bgmId, filters)`：只查已公开点评/推荐
- `aggregatePublicData(metric, filters)`：只读公开聚合指标，不接受任意 SQL、URL 或页面脚本
- `openWebView(view, params)`：只生成站内页面跳转意图，由前端在用户点击后导航

工具统一返回已校验 JSON；服务端负责账号范围、参数白名单、超时、限流、结果条数和错误分类。模型输出不会创建新工具，也不会获得数据库、源码、文件系统或浏览器控制权

### 7.2 追番变更

`proposeTrackChange` 生成对象、字段、旧值、新值和影响说明；用户点击确认后调用 `applyTrackChange`。写入带 revision、前置条件和幂等请求号，成功后回读权威记录并更新会话

### 7.3 播放源打开

`proposePlaybackOpen` 只返回番剧、源站、集数和将要打开的页面；用户点击确认后，前端携带 `actionId` 执行现有播放/解析流程。Agent 不直接请求源站

动作状态统一使用：

`prepared → user_confirmed → dispatch_started → navigation_committed → player_ready → source_selected → media_canplay → playing → completed`

允许的结束状态还有 `failed`、`cancelled`、`unknown`：

- 追番写入以“服务端响应 + revision 回读一致”为 `completed`
- 同源 Web 播放器用页面挂载、源绑定、`canplay`、`playing` 事件确认进度
- 新标签页或跨域源最多确认“浏览器已发起导航/窗口已打开”；跨域页面的实际播放状态标为 `unknown`，截图不作为成功证据
- 弹窗被浏览器拦截、源解析失败或播放器超时，分别记录 `failed`；没有完成事件时不报成功，显示“查看播放页 / 重新打开 / 用户已确认”
- 每个 `actionId` 的状态流在聊天卡片、目标页面和播放器之间关联；浮层隐藏后仍可恢复

## 8. AI 来源、模型门槛与运行上限

- **默认服务器 AI**：付费调用外部 DeepSeek API，默认模型为 `deepseek-v4-flash-vision-exp`（`DeepSeek-V4-Flash-Vision-Exp`）。只有基线评测达不到工具准确率、上下文理解或延迟目标时，才经维护者审批切换更强型号
- **BYOK**：用户自费填写 endpoint / model / key；平台只做接口能力探测和统一规则校验。BYOK 模型太弱时提示能力不足，质量责任归用户配置；平台不自动升级或切回另一模型
- **AI 来源范围**：只保留“项目默认模型 / 用户自配 API”两条付费路径；fake provider 只用于自动化测试
- **上下文上限**：支持 `64k / 128k / 256k / 1m` 有效档位，默认 `128k`；`1m` 是可按需展开的会话上限，不预填整段历史，实际请求始终受 provider 模型上限约束
- **工具轮数**：单轮最多 12 轮工具调用；达到上限先整理当前结果并等待用户继续，不继续盲目循环
- **时间策略**：取消原先 90 秒硬上限。单轮以 3 分钟为软目标、10 分钟为活动回合上限；超过 8 分钟显示长任务状态，10 分钟仍未结束则保存当前状态并转为可恢复任务，累计 30 分钟后要求用户继续或重新发起。连接层保留 heartbeat、idle 看门狗和有界重连
- 同一账号同时只运行 1 个 Agent 回合；模型调用、工具调用和压缩调用分别记录 token、耗时、结果数量与费用估算。服务器日志不记录完整对话、API key、Cookie 或私人正文

## 10. 验收条件

- 对话历史可跨设备恢复；用户能查看原始聊天，并用 `/compact` 或自动阈值压缩上下文，压缩不删除可见历史
- 用户确认的个人习惯/风格进入偏好卡片；未经确认的推测不会变成长期记忆
- Agent 新增界面符合手帐、可爱、和泉纱雾主题；右下角入口常驻，浮层可隐藏/显示，PC/平板横竖屏与缩放下页面宽度和主布局保持不变，手机端入口隐藏
- BYOK 只能替换模型请求，仍经过相同的系统规则、工具白名单、在线访问门槛、源码写入关闭和用户确认流程；自配模型不会获得项目控制权
- 相似番推荐只来自离线 BGM 索引或当前页面资料；周历、追番、公开大厅统计走只读数据工具
- Agent 运行期间不自动请求在线 BGM、稀饭、Girigiri；只有网页按钮点击后才产生对应网络请求
- Agent 没有源码、文件系统、shell、Git、部署和浏览器自动化写入能力；公开数据分析优先走只读聚合，方法示例只显示在聊天中
- 追番变更和播放打开都遵循“预览 → 用户确认 → 执行”；写入以回读确认，播放按事件链确认，跨域或缺事件时显示 `unknown`，截图不作为成功证据
- 默认服务器模型为 `deepseek-v4-flash-vision-exp`（`DeepSeek-V4-Flash-Vision-Exp`）；更强模型只在基线达不到目标且维护者审批后启用；本地部署项保持关闭
- 项目不设置免费 AI 档；fake provider 只用于测试，线上请求均走默认付费外部 API 或用户自配 API
- `64k / 128k / 256k / 1m` 档位按 provider 能力生效；`1m` 作为可按需展开的上限，默认自适应装配而非每轮填满；provider 原生压缩可复用时走原生，否则 DeepSeek 走应用 fallback；两条路径都保留完整历史
- DeepSeek 摘要 fallback 通过事实账本、双重校验、分层摘要、固定保留、版本回滚和按需原文回填保持长期会话连续性；摘要质量与 token 用量均有记录，压缩失败沿用上一版活跃视图
- 单轮最多 12 轮工具调用，活动回合上限 10 分钟并支持可恢复任务；价格预警金额由维护者配置，token/费用/硬停状态可观测
- AI/工具失败时，相关对话、查询条件和已生成正文保留；普通搜索与点评助手按钮只指向现有入口，不触发后台联网
- 20～30 条评测样例通过，PC 和平板浏览器各完成一次流式对话；每阶段都有独立测试记录和手动提交
