# 011 - 网页版在线观看

> 接手快照：2026-10-06，基于本地 `ac4ff2b` + 当时未提交工作区。本文从头整理，替代原来的累积纪要；**不是线上部署证明**。本轮只核对文档与代码，没有重跑真实播放验收。**日常接手只读本文；归档仅在追查原始证据时打开，不是必读前置。**

## 先看结论

**现在只有一张统一播放页：稀饭 / Girigiri → 服务端解析与媒体代理 → ArtPlayer。正在修的是起播、拖进度和持续缓冲，不是再选播放器架构。**

- 用户从追番卡片选片源进入；网站、站内线路、集数是三个不同概念。跨站靠各自绑定，不拿稀饭编号推 Girigiri 编号。
- 浏览器不再直接拉源站媒体；旧直连 → 探测 → 救援 → iframe、预转 HLS、慢源名额/候补均已撤掉。HLS **源文件代理**仍在，不等于旧 ffmpeg 预转。
- 当前工作区正在把 MP4「内存滑窗 + 独立下一集预取」收敛为「当前集和下一集共用落盘调度」。此快照中新增 `disk.ts`、删除 `prefetch.ts`，尚未提交；别按旧预取文档继续修。
- 本文只管 **Web**。桌面 `mtmedia://`、B 站 DASH、嗷呜、自定义 webview 的记录放在[原 011 归档](archive/011-在线观看-历史记录.md)，不是网页版已有能力。

**目标与范围**：以单人、iPhone Chrome 完整看完一集为主要验收，桌面浏览器也要回归；不重新引入多人带宽/准入方案，不把一次修播放器扩大为桌面端或搜索重构。

## 用户会经历什么

| 操作 | 当前行为与边界 |
|---|---|
| 从追番打开 | 已绑定直接用；稀饭未绑定/重绑进入搜索并由用户确认。旧站绑定需重新确认；新版稀饭不再走旧图片验证码。Girigiri 独立维护其搜索/验证码流程 |
| 默认集数 / 外跳 | 卡片显示 N 就播 N，0 从第 1 集开始，按已知总集数夹上限（`web/src/tracks/common.ts` 的 `watchEp`）；“跳去源站”是独立的用户选择，保留 `source-page` 接口，不是播放失败后的自动 iframe 兜底 |
| 进入播放页 | `/api/player/page?src=xifan\|girigiri&id=…&ep=…&bgmId=…`；本站未登录跳回追番。拿列表、线路及默认媒体地址，普通首次进入等待用户播放手势 |
| 默认线路 | 稀饭首次在符合条件的前两条可代理 MP4 间各测约 3 秒，取吞吐更大的；按用户会话/番缓存偏好，不是固定“线路二永远快”。HLS 不参测，播放中变慢不会自动换线 |
| 手动换线路 | 没解析过的线路才请求 `/resolve`；代次过滤旧结果。当前 `selectLine` 传入 **0 秒**并请求播放，仍可能受 ArtPlayer 进度记忆影响；没有显式传递切线前时间，不保证原时间点无缝切换 |
| 换源 / 换集 | 销毁当前播放器后整页跳转。跨源保持集号；未绑定源提示回追番绑定，缺集不猜另一集。没有 `bgmId` 的旧书签只显示当前源 |
| 起播 / 中途卡住 | ArtPlayer 自管初始加载；看门狗只在未暂停且时间约 1.2 秒未推进时显示“缓冲中 · 第… · 已缓冲…秒”，只收自己打开的圈，不再静音降速预热/拉回锚点 |
| 媒体出错 | 当前实现先同地址自动重挂一次，2 秒后重试并保留时间；再失败显示原因与手动重试。**这是现状，不是“全链路零重试”**，与重试预算规范的差距见下文 |
| 断网 | `offline` 保存时间和播放状态、暂停；`online` 后延迟一次检查本站 health，再在同线路恢复。没有周期性联网探测；媒体错误分流目前先依赖 `navigator.onLine` |
| 切后台 / 返回 | 隐藏时记 sessionStorage 进度；回前台不自动刷新、不查登录。标签页被浏览器回收重载后可读回 6 小时内快照；是否自动续播仍受浏览器限制 |
| 好看标记 / Agent | 有 `bgmId` 时读取这集的好看备注；带 Agent 播放上下文时发送页面就绪、媒体可播/播放/失败回执，不另造播放器 |

## 当前链路与代码入口

```text
追番卡片 / Agent 确认播放
  → 各站绑定 → /api/player/page → /playlist（手动换线才 /resolve）
  → 稀饭新站签发 / Girigiri 解析 → 带本站 HMAC 的媒体地址
  → ArtPlayer
      MP4 → /stream → faststart 虚拟目录前置 → disk 落盘读取
                                                └ 不适用时 stream 内存会话/透传
      HLS → /hls 改写子表、分片、key → /hls 或 /seg → 源站
```

媒体接口仍需本站会话，且校验解析层生成的 URL 签名；不是仅凭 URL 就能访问的开放代理。依赖从 `/api/player/vendor/` 自托管；监控 bundle 由 `web` 的构建脚本生成，dev 缺 bundle 时不能把“没有 Sentry”当成“没有故障”。

**两套登录分开看**：本站登录决定能否进入播放器；稀饭邮箱/密码登录决定源站资源权限。新站 token 放在按本站用户隔离的加密会话中，解析缓存带用户/会话代次，刷新单飞，登录/登出使旧请求失效。`AUTH_SECRET` 同时影响本站会话、稀饭会话解密和媒体签名，换密钥不是无感操作。源站要求登录、权限不足、限流应保留各自原因，不统一写成断网。

### 正在替换的 MP4 部分

**目录前置不转码**：若 moov 在文件尾，`faststart` 把尾块挪到 mdat 前并修正块偏移，对浏览器呈现总长度不变的虚拟文件。Range 再映射回原文件；按长度截断，避免重复吐出已挪走的尾块。Node 流先转 Web 流，销毁时取消底层读取。已是 faststart 就透传；结构解析失败后 60 秒内跳过改写。

**当前集也落盘**：符合 `canProxy` 的 MP4 优先走 `disk`；现名单为 `apn.moedot.net`、`play.xfvod.pro`。其它域名、超过单集上限或探不到长度的文件回到 `stream`。不能把“所有媒体经服务器”误写成“所有媒体都进磁盘缓存”。

| 工作区参数 | 实际含义（配置值，不是实测性能） |
|---|---|
| 全局 12 个 worker，256 KiB/块 | 当前集和下一集共享池；不是每集各 12 路。faststart 尾块另有最多 6 路，并不包含在这 12 路内 |
| 连续领先 1.5 MiB，起始闸门最多等 20 秒 | 只计算请求位置之后连续写完的块，不看总下载百分比；超时结束闸门也不保证马上已有可读字节 |
| 小 Range ≤1 MiB | 优先补请求涉及的块，不挪下载游标；其它 Range 仅最新读取端有权挪游标，避免旧连接来回抢位置 |
| 当前观看活跃窗口 2 分钟 | 最近被读取的未完成集优先；下一集仅在没有此类当前集时获分块下载名额 |
| 下一集延迟 30 秒解析 | 只对稀饭且列表确有 N+1 调度；MP4 且可代理才落盘。延迟解析/探长度仍可能与当前集共用入口，不是完全零干扰 |
| 单集 1.5 GiB；回收目标 4 GiB | `DATA_DIR/prefetch/`；块写完才置完成位，整集关句柄后 `.part` 改名；重启丢弃未完成文件。4 GiB 是回收目标，不是已证明的并发硬上限 |

与 09-23 旧预取的差异：不再是“等 60 秒、另开 4 路、整集下完才读”；现在未完成文件也能按已写块服务播放器，下一集复用同一套调度。缓存按**完整媒体 URL**哈希，新签名地址能否复用旧文件需另验。

## 已经踩过、后续别重来的结论

| 不再走的弯路 | 保留下来的原因 / 今天的处理 |
|---|---|
| 再叠直连、救援、预转、iframe | 旧链路每次换 `src` 都可能重置进度，各层回退在 iOS 上互相触发，最终 iframe 还可能落到广告页；统一服务端媒体入口是为了减少状态组合，不只是换外观 |
| `pause()` 后等浏览器攒满任意目标缓冲 | 历史 Chromium 样本在约 2.3 秒缓冲就停拉；静音低倍速预热又造成隐藏播放/进度倒退。现在缓存交给服务端，暂停不承诺浏览器继续拉流；暂停时 `timeupdate` 不动也不等于后台没下载 |
| 用 `seeked` / `progress` 当作已经恢复播放 | iOS 可能立刻发 `seeked`，收到一点字节也会发 `progress`；圈提前收掉后仍黑屏。看实际播放时间是否推进，并区分首次加载圈与看门狗自己的圈 |
| 把每个 Range 都当成用户拖动或重复下载 | 浏览器会探文件头、取尾部目录、暂停断流再续读；先核对请求位置与缓存命中。小探测别驱逐主下载，旧内存路径保留 15 秒重连宽限；新 disk 路径用小请求优先队列 |
| 把 `video code=4` 直接翻译成“地址过期/编码不支持” | 历史根因还包括代理 502、上游对 Range 回 200、旧实例销毁时的迟到错误；先查响应状态和播放器代次。HTTP 200 兼容与 4xx/5xx 重试是两件事 |
| 源站能播就凭旧域名/端口规则改地址 | 对照当时官方播放器实际媒体请求；新稀饭逐集签发、保留真实集号，缺集不重新编号、OVA 不覆盖正片。旧端口结论、旧编号和模板地址都不迁回新协议 |
| 拿一个速率判断所有瓶颈 | 分开看源站→服务器、服务器→设备及媒体码率；历史 10-03 样本入口约 5Mbps、该集约 2.2Mbps，预取也共享入口。并发只在实际有收益的链路用，平均够快不等于慢段不断流 |
| 照搬旧页面 CSP / 手机布局 | 当前 ArtPlayer 需要内联样式，仅播放页 `style-src` 放行，脚本仍用 nonce；不能按旧方案一刀切禁样式或连脚本一起放开。保留 no-referrer，手机高度按 `100lvh`，固定元素避免动态 safe-area 布局；iOS 系统全屏看不到页面 DOM 缓冲文案 |

## 现在继续修：先验这些边界

当前源码能确认“有这段逻辑”，不代表它已经可靠。下面是接手检查表，不把待查问题当成已复现事故。

- [ ] **冷起播与持续播放**：新番尾部 moov / 旧番头部 moov 各测；iPhone Chrome 与桌面各走“加载 → 暂停待点击 → 首次 playing → 后续 waiting/seek”。必须有整集样本，不能只看平均速率或几秒截图。
- [ ] **Range / 落盘**：往前、往后、反复拖动；新位置大 Range 与文件头小 Range 交错；未完成 `.part` 到整集改名；取消读、暂停、换集和重启。核对 206/416、Content-Length、字节一致性及旧请求退出。
- [ ] **跨层重试预算**：hls.js 已配零重试，但 `page.ts` 对媒体错仍自动重挂一次，`stream.ts` 有传输重试；`disk` 分块遇 4xx/5xx 终止，而探长度失败会返回 null 再走旧在线路径。需要查同一上游失败是否被别层再打，不能在文档里统称“不会重试”。
- [ ] **取消与过期结果**：`lineRequest` / `generation` 只过滤旧结果，不等于中止网络请求；`boot/selectLine` 的 fetch 没传 AbortSignal。`disk.schedulePrefetch` 是延迟任务，当前没带用户 owner/取消句柄，不能沿用旧版“每人只留最新一个、换番即撤销”的保证。
- [ ] **落盘边界**：写调用返回的 `bytesWritten` 未逐次核对；空间回收没有已验证的活跃读取保护/硬容量门禁；错误时关写句柄与其它 worker 收尾是否竞态，需要定向复现。20 秒起始闸门不是整条读取 deadline，`cancel()` 是否唤醒等待中的读取也要验。
- [ ] **恢复与权限**：断网/恢复、后台停留、浏览器前进后退缓存（bfcache）、系统回收、本站会话过期、源站 401/403/429/5xx；恢复继续使用旧媒体地址，地址失效与全局断网要分开。9 月记录中真实稀饭账号与受限资源尚待验，本轮没有补验。
- [ ] **Girigiri 回归**：HLS manifest/子表/key/分片、原生 HLS 与 hls.js 两条分支、切源同集。不要用稀饭 MP4 的结果代替 Girigiri 验收。

**最快的排查顺序**：

1. 记源、番、集、线路、设备、操作和时间；先分清“搜索/解析慢”“目录没拿到”“Range 首字节慢”“连续缓冲不足”。
2. 看终端：`[player:client]` 还原用户动作和胶片；`[player:req]` 看 Range / 首字节 / 字节量 / 结束原因；`[player:faststart]` 看目录；`[xifan:disk]` 看块进度。工作区新增 QoS 会区分普通卡顿、起播耗时和 seek 等待，尚待验证。
3. 按真机 Range 顺序做本地重放，再回原设备验；记录原命令、输出、样本和未覆盖场景。不要用源站测速、类型检查或构建成功代替播放成功。
4. 涉及稀饭新站协议可用现有 `web/scripts/test-xifan-next.ts` 夹具；它验证解析/协议，不验证真实账号和整集播放。诊断用 `/api/player/probe` 也不等同完整播放页验收。
