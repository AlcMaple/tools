# 手机白屏 / 地址栏一直转 —— 通用排查与修复指南

一次真实排查的经验抽成可复用的东西。本项目（`anime.alcmaple.cn`）已按此实现，代码见
`web/server/node.ts`（自愈路由）/ `web/index.html`（脚本队列）/ `web/public/white-screen-probe.js`（兜底探针）。

这份文档的用法：

- **本项目再犯** —— 照 §1 分诊，看落到哪一类，对应的实现已经在了，直接验收。
- **另一个项目 / 另一台服务器** —— 「§2、§3 照抄」原样搬，「§4 每实例单独生成」逐项走，
  再按「§5 顺序」拼起来、按 §5 的验收清单收尾。
- **想先确认自己是不是这个病** —— 只看 §1。**没做 §1 就动手改代码，前面几轮全部白改**（见 §7）。

适用范围：**带 hash 文件名的前端构建产物 + 单页应用**（Vite / webpack / Rspack / Parcel 皆同），
自有服务器或任何能自定义 404 响应的托管。纯静态托管平台的替代做法见 §6。

---

## §0 症状形状

```
手机浏览器（Chrome iOS / Safari / 各家内核）
  ├─ 打开站点，正常
  ├─ 切走 / 另开标签 / 杀掉浏览器进程
  └─ 切回来  ──►  整页纯白，地址栏进度条一直转，手动刷新才恢复
                   桌面浏览器完全复现不出来
                   Sentry / 前端监控一条事件都没有   ← 关键线索
```

**「监控一条都没有」不是监控坏了，是页面里一行 JS 都没执行。**
这一条直接排除掉所有"在 JS 里加兜底"的思路 —— 兜底代码本身也不会跑。

---

## §1 分诊（唯一决定性的一步）

白屏有好几种成因，长得一模一样，猜是猜不出来的。**去服务器 access log 找那一刻的请求序列。**

拿到用户复现的墙钟时间，换算成服务器时区（`date` 一下，别默认同区）：

```bash
# nginx 为例；时间窗口取前后各 5 分钟，UA 筛移动端
grep -E "04/Sep/2026:17:3[5-9]|04/Sep/2026:17:4[0-9]" /var/log/nginx/access.log \
  | grep -iE "iphone|android|mobile" | tail -60
```

对照下表判断。**判据是「有没有 HTML 文档请求」，不是「有没有 404」**：

| 日志形态 | 病名 | 去 |
| --- | --- | --- |
| **没有 `GET /`**，直接从子资源开始，入口 `index-<hash>.js` 404 | 陈旧标签页快照 | §2 |
| 有 `GET /` 200，子资源也全 200，但页面还是白 | 脚本执行被阻塞 | §3 |
| 有 `GET /` 200，入口 JS 200，但 CSS/字体 404 | 构建产物不完整 | 查发布流程，本文不覆盖 |
| 连 `GET /` 都没有、子资源也没有 | 请求没到服务器 | 查 DNS / nginx / 网络，本文不覆盖 |

本项目实测命中第一类，日志长这样：

```
17:41:44 GET /                          200   ← 正常访问（对照组）
17:41:44 GET /white-screen-probe.js?v=2 200
17:41:45 GET /assets/index-DjdfCJrX.js  200
...
17:42:03 GET /assets/sagiri-full.webp   200   ← 白屏这次
17:42:03 GET /assets/index-qKyKiqvz.css 404   ← 旧 hash
17:42:03 GET /assets/index-BdKVCKNd.js  404   ← 旧 hash
                                              ← 全程没有 GET /
```

**含义**：手机浏览器恢复被杀掉的标签页时**不重新请求 HTML**，而是还原它自己序列化的旧 DOM 快照，
再按快照里的 URL 去取子资源。快照可能是好几次部署之前的，其中带 hash 的入口文件早已不存在
→ 入口脚本 404 → 什么都没执行 → 白屏 + 进度条空转 + 监控静默。

## §2 照抄：陈旧入口自愈（治第一类）

### 做法

**未知 hash 的入口脚本不返回 404，返回一段合法的、会重新载入页面的 JS。**
浏览器照常执行它 → 拿到当前的 HTML → 白屏自己消失。

Hono / Node 版（本项目实现，其他框架照搬语义即可）：

```ts
const STALE_ENTRY_RECOVERY = `// 这份资源属于一个已经下线的构建版本：当前页面是浏览器还原的旧快照。
(function () {
  var GUARD = 'mt_stale'
  try {
    var url = new URL(location.href)
    if (url.searchParams.has(GUARD)) {
      console.error('[stale-entry] 重新加载后仍然是旧入口，停止重试')
      return
    }
    url.searchParams.set(GUARD, Date.now().toString(36))
    location.replace(url.pathname + url.search + url.hash)
  } catch (_) {
    location.reload()
  }
})()
`

app.get('/assets/*', (c) => {
  if (/^\/assets\/index-[A-Za-z0-9_-]+\.js$/.test(new URL(c.req.url).pathname)) {
    return c.body(STALE_ENTRY_RECOVERY, 200, {
      'Content-Type': 'application/javascript; charset=utf-8',
      'Cache-Control': 'no-store',
    })
  }
  return c.notFound()   // 其余未知资源保持 404
})
```

### 四条红线（照抄时一条都不能省）

1. **一次性守卫参数**（`mt_stale`）。没有它，万一服务器真的坏了、`/` 也返回旧 HTML，
   就是一个无限重载循环 —— 比白屏还糟。
2. **`Cache-Control: no-store`**。这段脚本占用的是一个「带 hash」的 URL，
   如果项目对 hash 资源发 `immutable`，这段自愈脚本会被浏览器按那个 URL 缓存一年。
   同时**缓存头中间件要加守卫**，别把这条 `no-store` 又改写回 `immutable`：

   ```ts
   app.use('/assets/*', async (c, next) => {
     await next()
     if (c.res.status !== 200) return
     if (c.res.headers.has('Cache-Control')) return   // ← 就是这一行
     /* ...原来的 immutable / must-revalidate 逻辑... */
   })
   ```
3. **只匹配入口脚本**，不要泛化到整个 `/assets/*`。入口是快照里必然被重新执行的那一个；
   把范围放大，等于任何拼错的路径都触发一次整页重载。
4. **入口 HTML 必须 `no-cache, must-revalidate`**。自愈的下一步是重新取 HTML，
   HTML 要是还能被缓存，就取回同一份旧的，守卫一挡就彻底不动了。

### 为什么不是"部署时保留旧 hash"

那是最容易想到的方案（Vite 的 `build.emptyOutDir: false`、webpack 不清 dist），**并且救不了**：
快照可以比任何保留窗口都旧。本项目实测那次，快照引用的文件是**引入保留策略之前**的产物，
早被删了。而代价是 dist 无限累积。已回退。

保留旧 hash 只能缩小窗口，自愈是兜住全部。要做也是做自愈。

## §3 照抄：别让第三方脚本挡住入口（治第二类）

### 规则

**`<script defer>` 的经典脚本和 `<script type="module">` 共用同一条「延迟脚本」队列，
按文档顺序执行。** 打包器（Vite 等）通常把入口 module 注入到 `<head>` 末尾 ——
排在它前面的任何 `defer` 脚本，只要卡住，入口就永远轮不到执行。

所以：**页面里所有第三方脚本（统计、客服、A/B、广告）一律 `async`，永远不用 `defer`。**

```html
<!-- 错 -->
<script defer src="https://third-party.example/script.js"></script>
<!-- 对：async 把它移出延迟队列，入口不再等它 -->
<script async src="https://third-party.example/script.js"></script>
```

绝大多数统计脚本是自初始化的，`async` 下功能不变。真需要保证执行顺序的第三方脚本，
改成在应用挂载**之后**用 JS 动态插入，而不是留在 HTML 里挡路。

### 严重性怎么估

阻塞时长 **= 第三方脚本的挂起时长，没有上限**。手机从后台恢复时复用陈旧连接、
挂到 TCP 超时就是几十秒。本项目那个统计脚本在桌面网络下 TLS 握手 0.36~1.77s、
总耗时 1.6~2.8s —— 一切正常时它已经是首屏最慢的一环。

### 顺手检查

同样的队列语义也意味着：**入口 HTML 里排在打包器注入点之前的任何同步 `<script>`，
都在首屏关键路径上**。白屏探针这类必须最先跑的除外（它就该在最前面且体积极小）。

## §4 每个实例单独生成的部分

照抄 §2/§3 之前，这几项**必须按自己的项目重新确定**，抄错了修复不生效：

| 项 | 怎么确定 | 本项目值 |
| --- | --- | --- |
| **A. 入口脚本的 URL 形状** | 构建一次，看产物 HTML 里 `<script type="module" src>` 的实际路径 | `/assets/index-<hash>.js` |
| **B. 入口正则** | 按 A 写，**必须锚定 `^...$`**，且只匹配入口不匹配其他 chunk | `^/assets/index-[A-Za-z0-9_-]+\.js$` |
| **C. 静态资源目录前缀** | 打包配置里的 `build.assetsDir` / `output.publicPath` | `/assets/` |
| **D. 守卫参数名** | 取一个项目内不会撞的名字，避开业务已用的 query | `mt_stale` |
| **E. 缓存头中间件的位置** | 找到给 hash 资源发 `immutable` 的那段，在里面加守卫行 | `server/node.ts` 的 `app.use('/assets/*')` |
| **F. 404 兜底的注册顺序** | 自愈路由必须**在**静态文件中间件**之后**（真实文件优先），**在** SPA 兜底 `app.get('*')` **之前** | 见 `server/node.ts` |
| **G. 第三方脚本清单** | `grep -n "<script" index.html`，逐个确认 async | 统计脚本一个 |
| **H. 日志路径与时区** | `ls /var/log/nginx/`、`date` | `/var/log/nginx/access.log`，UTC |

**F 最容易错**：注册顺序反了会出现两种坏法 —— 放太早，真实入口文件也被自愈脚本顶掉，
线上直接死；放太晚（在 SPA 兜底之后），未知 JS 路径被兜底成 HTML，浏览器报 MIME 错，等于没修。

## §5 换个项目 / 服务器：顺序

1. **先分诊**（§1）。拿到 access log 证据再动手。没证据就改代码 = 重蹈 §7。
2. 填 §4 的 A~H 八项。
3. 按 §3 把 HTML 里的第三方脚本改 `async`。
4. 按 §2 加自愈路由 + 缓存头守卫行 + 确认 HTML 是 `no-cache`。
5. 按 §6 在本地跑两个复现实验，**改完必须在本地看到"先白后自愈"这个过程**，不能只靠线上肉眼。
6. 部署前备份，部署后按下面的验收清单逐条 curl。

### 验收（通用，跟平台无关）

```bash
# 1. 未知入口 hash → 200 + no-store + 是一段 JS（不是 404，不是 HTML）
curl -si https://<host>/assets/index-DEADBEEF.js | grep -iE "^HTTP|^cache-control|^content-type"

# 2. 现役入口 → 仍然 200 + immutable（自愈路由不能顶掉真实文件）
curl -sI https://<host>/assets/<真实hash>.js | grep -iE "^HTTP|cache-control"

# 3. 其他未知资源 → 仍然 404（范围没被放大）
curl -s -o /dev/null -w "%{http_code}\n" https://<host>/assets/nope-abcdefgh.png

# 4. 入口 HTML → no-cache
curl -sI https://<host>/ | grep -i cache-control

# 5. 第三方脚本 → async
curl -s https://<host>/ | grep -o '<script [^>]*src="https\?://[^"]*"'
```

五条全对才算完。第 2 条尤其重要 —— 它是"没把线上改死"的证明。

### 真机复测的陷阱

**坏掉的那个标签页现在切回去就会自愈，所以它测不出东西。** 要真正验证，得重新造一个陈旧快照：

1. 手机正常打开站点；
2. **重新部署一次**（让入口 hash 变化）；
3. 杀掉浏览器进程、重开；
4. 切回步骤 1 那个标签页。

跳过第 2 步的话，快照里的 hash 仍然有效，本来就不会白屏。

## §6 本地复现实验（不用等真机）

两个实验，都不需要手机，几分钟能跑完。

### 实验 A：陈旧快照（验 §2）

起一个静态服务，**第一次**请求 `/` 返回「把入口 hash 换成一个不存在的值」的 HTML，
之后返回正常 HTML；`/assets/*` 未命中的转发给你真实的应用服务器（让它决定 404 还是自愈）。

浏览器打开 → 期望看到：地址栏自动变成 `/?mt_stale=...`，页面正常渲染。
用 `document.getElementById('root').innerHTML.length` 确认不是空壳。

修复前的对照：同样的页面停在白屏，`#root` 长度为 0。

### 实验 B：脚本挂起（验 §3）

把第三方脚本的 `src` 换成一个**同源**的路径（避开 CSP），服务端对这个路径 `sleep 60` 不返回。
起两份，唯一差别是 `defer` / `async`，对比：

```js
Math.round(performance.getEntriesByType('navigation')[0].domContentLoadedEventEnd)
```

本项目实测：`defer` → **60054 ms**（就是那个 sleep 值，说明完全被它拖着）；
`async` → **22 ms**。HTML 自身 `responseEnd` 两边都是 ~10ms，排除服务器慢。

> 注意 60054 是实验里人为设的挂起时长，不是线上实测值。它证明的是
> **阻塞时长等于第三方脚本的挂起时长、没有上限**。

### 静态托管平台（Vercel / Netlify / OSS）怎么办

改不了 404 响应体的平台，退而求其次，按优先级：

1. 平台支持重写规则的，把未知 `/assets/index-*.js` 重写到一个固定的 `/stale-entry.js`
   （内容就是 §2 那段脚本，配 `no-store`）—— 等价效果。
2. 支持 Edge Function / Middleware 的，在那里实现 §2 的逻辑。
3. 都不行，才退回"保留旧 hash + 白屏探针 watchdog"的组合，并接受它只能缩小窗口。
   探针必须放在 HTML **最前面**（早于打包器注入点），否则它错过入口脚本的 error 事件。

## §7 为什么前面几轮修复全部无效（改之前先读）

本项目在找到真因前试过四轮，全部无效，且**每一轮都能自圆其说**。记下来是为了别再走一遍：

| 试过的 | 为什么没用 |
| --- | --- |
| 监控 SDK 的动态 import 改成非阻塞 | 主包压根没开始执行 |
| HTML / 探针加 `no-cache`，未知资源单独 404 | 这次连 `GET /` 都没发出去 |
| 保留旧 hash（`emptyOutDir: false`） | 快照比保留窗口更旧，文件早删了；见 §2 末 |
| 白屏探针 watchdog 自动重载 | 旧快照里装的是**旧版探针**，没有 watchdog；而且它在 body 末尾，晚于入口脚本，错过 error 事件 |

**共同的错**：全都假设"页面里有代码在跑"。而 §0 那条线索（监控一条事件都没有）
早就否定了这个前提。

另一个反复踩的坑：**桌面 Chrome 正常不构成任何证据**。这一类问题的触发条件
（进程被杀、标签页快照还原、陈旧连接复用）在桌面上基本不出现。

**唯一可靠的顺序永远是：先拿 access log 请求序列，再定病，再改代码。**
