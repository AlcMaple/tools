# 2026 接单评估

## 2026-11-09 fix(order-judge): 流程图改成可缩放平移的画布

**修改后效果**
- 流程图每一层固定一行，不再因为一层放不下换到下一行；放不下就整体缩小适应宽度，开发者侧编辑时右上角有「还原」
- 放大：滚轮加 Ctrl（Mac 是 ⌘）；平移：拖空白处；动过之后不再自动适应，双击空白处恢复；触屏不能缩放和平移
- 所有连线常驻：每个功能连到上一层最近前置的是实线，跨层或多个来源的次要线是更细更淡的虚线；悬停某个功能时它的线加粗，其余变淡；A→B→C 已成立时不再另画 A→C
- 「按模块填实际小时」改成整行列表：需求名占满左边自动换行，输入框和「小时」靠右对齐，手机宽度下同样一行

**关键决策**
- 上一版想「次要线悬停才画」，离开就消失，实测不好用；真正乱的是同一层换行后多出的横向通道，换成每层一行就不需要藏线了
- 画布缩放用整块 transform，连线测量时把屏幕坐标除以缩放比换回舞台坐标；拖节点、拉线同理
- 节点最宽 220px，长标题自己换行，避免一层被撑得太宽导致缩得太小

**边界 / 风险**
- 某一层节点很多时整体会缩得较小，需要放大看字；缩放下限 30%，上限 250%
- 触屏不能缩放和平移，窄屏只能看自动缩小后的样子；浏览器里没实测，只过了类型检查、算法测试和构建（内置浏览器连接超时，本机没装 Playwright）
- 长跨层连线仍会从中间层节点的缝隙穿过

## 2026-11-09 feat(order-judge): 成交后可按模块填实际小时，校准改为汇总全站项目，流程图去掉多余连线

**修改后效果**
- 成交后「做完后填」多一栏「按模块填实际小时（可选）」，每个要花时间的需求一行，占位显示 AI 估的小时；不填照旧，只填整类用时也行
- 填了的模块直接当这条的实际，没填的分整类实际扣掉已填后的余量；每个要花时间的模块都填了而整类留空时，合计当作整类实际；只填一部分不会被当成整类
- 时间值、小时系数、各类工作的修正（确认 / 验证 / 接手 / 上线）改为汇总所有用户的项目来学：每类客户最近动过的 50 个项目，不再只看自己的。「系统目前学到了什么」里的单数是全站的
- 每个人仍只能看到自己的项目；给 AI 的「历史条目经验」仍只用自己账号的条目标题；不愿贡献的项目整个不进汇总
- 流程图：A→B→C 已经成立时不再另画 A→C，中间的功能没选才保留（那是真缺东西）；没悬停时线条淡一些，悬停某个功能时该功能的线加粗，线多时靠这个看清谁连谁

**关键决策**
- 汇总在服务端做，只把算出来的时间值、系数和说明发给前端，别人的项目数据不下发；汇总只读版本里的清单和报价，不含原文、图片、附件和标题
- 结果缓存到任何人保存为止（最长 10 分钟），保存后下一次打开就包含新数据；汇总取最近更新的 1000 个项目的版本
- 按模块实际只影响「条目级」的学习（每类工作的小时修正、给 AI 的经验），整类小时系数仍用整类实际；这样不会因为只填了一个模块就把整类系数拉偏
- 画线只做视觉去冗余，冲突检查仍用完整依赖，客户去掉前置功能时仍标红

**边界 / 风险**
- 前端优先用服务端的汇总，没有时（桌面端）仍只用本机项目，桌面端没改，也没有按模块填的输入框
- 目前用户很少，汇总和个人结果几乎一样；人多后一个人的极端数据会被中位数摊薄，但「最近 50 个」按全站时间排，活跃用户会挤掉别人
- 样本不分行业，所有人的小时共用一套系数；如果接单类型差别很大，要再按项目类型分组
- 流程图只验证了类型检查和构建，没在浏览器里看实际效果；浏览器回归需要 Playwright，本机没装
- 新提示词和汇总没用真实多用户数据验证

## 2026-11-09 feat(order-judge): 流程图可拖动连线，单项工时可直接输入并限 7 天

**修改后效果**
- 客户确认页的流程图：拖节点换位置，从节点底部圆点拖到另一个节点加一条「要先有」，点线删掉，右上角「还原」恢复；手动加删的线参与「需要先有…」的冲突检查，只在当前页面有效，刷新还原，不随提交发送
- 整理需求时，同一件事要在多个分身、窗口里各做一遍只写一条，数量写进标题，不再每个分身各列一份串进流程
- 报价状态「已报价」下，客户结果多一项「同意」，只做记录，不改状态、不进校准统计
- 成交后回填的两栏改名：「从零做的部分用时」「验证和改旧代码用时」
- 单项工时：滑块固定 0～7 天（56 小时），数字可点开直接输入；到 7 天时提示「建议把合作方式改成长期」

**关键决策**
- 单项上限统一用 `ITEM_MAX_HOURS`，滑块、输入框、整体倍率、保存校验共用一个值；原先滑块上限 `max(16, AI 估计 × 3)` 会让小项被卡在 2 天
- 整体倍率是按 AI 估计相乘，AI 估 0 小时的条目放大后仍是 0，这是原有口径，没改
- 流程图拖动用 transform 位移，连线继续靠量 DOM 重新走线，所以拖动后自动避让

**边界 / 风险**
- 基础 / 推荐 / 完整三档仍在，报价条还显示「基础档」，是否改成一口价待定
- 分身去重只改了提示词，已有清单不变，没用真实 AI 验证
- 流程图拖动没在浏览器里实测；开发者侧流程图仍只读
- AI 原始估计超过 7 天的条目，没动过时报价仍按 AI 原值算

## 2026-11-07 feat(order-judge): 客户可通过链接确认需求，长期项目改按月固定费

**修改后效果**
- 整理后先进需求阶段：只看多个互斥方案（选一条路，不是分期或大小档，方向已定时只给 1 个方案）、流程图和要问的问题；客户确认或你直接选定方案后，才出现必须 / 不做 / 不包含和估价
- 项目里可生成免登录链接发给客户：客户选方向、勾选功能、看功能怎么连起来、自己加需求、回答问题后提交；看不到价格和小时
- 客户去掉前置功能时流程图标红，写明缺什么，可一键补回，也可以照样提交，开发者这边看得到冲突
- 开发者点「按这份生成新版本」后，确认项转必须、没勾的进不包含，报价只出一份范围
- AI 判断项目是一次性还是长期，开发者可覆盖；长期单不报总价，月费 = 每月投入小时 × 时间值 + 支出，客户版写明第一个月交付什么；没有依据时按清单小时摊 3 个月给粗估

**关键决策**
- 客户文字不可信：id 只认这一版清单里的，AI 只估新增条目和吸收回答，范围由程序确定，改不了
- 清单出新版本后旧链接作废；AI 估算期间客户又提交时拒绝应用，不用旧内容覆盖
- 详见 [022](../ideas/022-客户确认需求与长期合作.md)

**边界 / 风险**
- 方案、依赖、合作方式的提示词没有用真实 AI 验证，只跑过夹具
- 链接不进备份，恢复备份会丢掉未应用的客户提交
- token 在接口路径里，会进 nginx 访问日志
- 只改网页版，桌面端不显示新面板
- 层内换行时连线可能从节点背后穿过

## 2026-11-05 fix(order-judge): 实际报价填 0 保存后不再消失

**修改后效果**
- 实际报价填 0 并保存后，输入框保留 0，报价单也按 0 出价，不再回到「默认 50」的占位状态

**关键决策**
- 原因是归一化把 0 当成空值写成 null；现在只有留空才是 null，算报价单时也用「是否为 null」判断，不再用真假判断
- 桌面端共用同一份归一化，一并生效

**边界 / 风险**
- 没跑 `test:order-judge-quote`（环境未装依赖），也没有为 0 补专门用例

## 2026-11-05 fix(order-judge): 论文和读代码不再按人工时估，时间值统一从 67 起步

**修改后效果**
- 论文、报告这类纯文档单，每章都算 AI 直接写好，只单列一条人工核对，整份 0.5～3 小时；真实 AI 回测同一份论文单从约 29 小时、¥2,430 降到 3～5 小时、¥260～¥420，实际是 3 小时，报 ¥288，成交 ¥200
- 改别人代码时，AI 读代码和修改都不计时间，只算环境、问规则、回归验证这些人绕不开的部分；标签改成「旧系统里要人做的」
- 所有客户类型的时间值起点从 31 / 267 统一成 67；同一份团购需求的回测报价从 ¥8,770 降到 ¥3,650
- 保修和售后答疑不再单列条目

**关键决策**
- 67 来自目前唯一的真实成交（¥200 ÷ 3 小时，开发者觉得值），这单只用来定起点，不进行情样本
- 宁可从低处起步：报低了做完选「亏」能抬上去，报高了客户直接走人，要嫌贵满 3 单才会压价

**边界 / 风险**
- 67 只来自一单学生论文，商单很可能偏低，要靠成交后回填修正
- 回测用的正是调提示词时看的那一单，不算独立验证；其他文档单和代码单是否准确要等新单子
- 「保修不单列」没有用真实 AI 重跑；论文单 AI 仍常把 kind 标成接手改，时间值统一后暂不影响价格，以后两档拉开时论文类的核对时间可能按高价算
- 算法测试仍用 31 / 267 两档，才测得出新做和接手有没有算混

## 2026-11-04 feat(order-judge): 小时可用滑块调整，客户版按判断分项列价

**修改后效果**
- 新增同类行情：AI 给每单标项目类型，成交和客户拒绝的结果匿名进样本库；同类型同客户类型近一年凑够 3 单才显示「多数在 ¥X ～ ¥Y」，不够时明说是粗算
- 用户的项目不再自动删除（原来超过 50 个会删最久没动的），校准只用最近动过的 50 个
- 相邻两档价差不到 1 成时合并成范围大的那档；自用版开头去掉时间值来源，移到「系统目前学到了什么」；算法全貌见 `docs/web/接单评估算法说明.md`
- 校准不再被单笔带偏：亏和值取中位数；客户嫌贵攒够 3 单会压低时间值，和亏冲突时取中间；小时系数攒够 3 单才生效
- 新增实际报价：填了就只报这一个价，分项按比例摊；已报价或已成交时可选不贡献，默认匿名贡献
- 报价区顶部实时显示各档价格，默认不用动就能出价；一根「整体」滑块（× 0.5～2）缩放全部小时，单项滑块只露出占钱 80% 的条目，其余收起，拖过的一直露出，8 小时起按天显示，可一键恢复 AI 的估计
- 需求清单不再显示小时，小时只在滑块里看和改；离开草稿后滑块锁定
- 每条需求标出小时花在哪：确认 / 验证 / 接手 / 上线 / 直接做。客户版把「交付」拆成需求确认、可行性验证、接手旧代码、上线保障分项列价，加起来等于报价，仍不露小时；只有最低收费时仍叫「交付」
- AI 整理时：涉及收钱、真实用户数据、第三方额度、数据迁移、高峰流量的，必须单列上线条目；对客户在意的结果没帮助的，优先级不高于「可以」
- 验证可行性改按接手改的高时间值（默认 267）算，确认和上线仍按 31；直接能做的再多也只收最低收费，价差来自要验证多少
- 保存滑块后，小时系数以最后保存的值为校正样本，没拖的条目算认可；没拖就报出去也算一次认可，未处理的草稿不算；做完填了实际小时的以实际为准
- 每天投入默认改为 8 小时；不常用的设置收进「更多设置」，已填过的打开时展开
- 修复：追加版本没有任何变更时，变更单也收 ¥50 最低收费

**关键决策**
- 依据文章第三条和 Shopify 说 AI 没改变的三个难题（做什么、为什么值得做、怎么在真实用户面前站得住），口径见 `docs/ideas/021-接单评估重新定位.md`「滑块与判断分项」
- 拖的值存在每版的报价设置里，不改 AI 的清单，恢复和比对都有原值；拖过的小时不再乘历史系数；每个项目只算一个样本，没拖的条目算认可
- 变更单从空白设置开始，AI 小时没变的条目沿用成交时调定的小时，否则调低过的条目会被重复收费

**边界 / 风险**
- 新提示词没用真 AI 跑过，判断分类和上线条目的质量未验证；测试用的是假 AI
- 样本只含类型、价格、结果、预算和月份，与账号不可关联；用户删项目时样本一起删，注销账号时匿名样本保留
- 上线初期没有行情，所有价格都是粗算；目前只有开发者一人使用，行情就是自己的历史成交，以后有其他用户再考虑人数门槛
- 价格很依赖 AI 把哪些小时标成验证，没用真 AI 验证过；267 来自假设题，要靠成交回填修正
- 老项目的每天投入仍是保存时的值，判断分类按小时、接手、未说清推断
- 桌面版只过了类型检查，没在真机 Electron 里点过

## 2026-11-04 feat(order-judge): 报价改按要想多久计价，客户类型手选，新增工期和最低收费

**修改后效果**
- 整理前先手选客户类型（商单 / 学生单 / 个人单），选择会记住；没选就提示「先选客户类型」，不再由 AI 猜
- 小时只算「人要花的时间」，不算写代码：直接能做的功能 0 小时，需求没说清要确认、要先验证可行性、要读懂别人旧代码才计小时。三个直接能做的功能只收最低收费 ¥50，三档价格一样时只留范围最大的一档
- 学生单、个人单没有兜底，14 天保修照给，报价单写明不另外收费；商单保持原样
- 新增工期：各档总小时 ÷ 每天投入（默认 4 小时，可改）得出预计几天；填了截止日（材料里的「12 月 20 日」「明天」会自动读成日期，也可手填）就逐档判断来不来得及，赶不上时指出哪一档能赶上。客户版只写「预计 N 天交付」，不加急加价
- 去掉「不找你会怎么办」；「预算」改叫「客户预算」
- 追加需求后输入区收成一条，需求清单和报价并排显示，不再左侧大片空白
- 修复上一次提交（eb898af）遗漏的桌面端错误卡片：它仍引用已删除的 `openWeb`，桌面端编译不过，现已去掉那个「去网页版设置 AI」按钮

**关键决策**
- 口径来自开发者 2026-11-04：AI 写代码、处理边界和安全近乎零，真正的成本是想清需求和验证可行性；功能可行后实现是秒级的。所以价格跟着「要想多久、多不确定」走，简单需求只象征性收费
- 不做加急加价：客户看重价格，加价反而不想做；截止日只用来判断来不来得及，并回答客户「多久能做完」
- 客户类型走请求体（`clientType`），服务端强制写进需求清单，网页和桌面一起改，必须一起上线

```
手选类型 → 随材料交给 AI（小时只算人的时间）→ 逐条小时 × 时间值
        → 不足最低收费就按 ¥50 → 三档（同价留大范围）→ 各档小时 ÷ 每天投入 = 工期
        → 和截止日比：来得及 / 哪一档能赶上 / 来不及
```

**边界 / 风险**
- 最低收费 50、每天投入 4 小时都是默认值，未经实测；每天投入可在报价面板改，最低收费目前只能改代码里的默认设置
- 小时数仍由 AI 估，提示词里给了分档口径，但是否估准要靠成交后回填实际小时校准；没用真 AI 验证过
- 变更单里只有直接能做的新增功能时，也会收最低收费，是否合适待观察
- 旧版本（没有手选类型）的项目，「待确认」类型仍按商单口径算兜底
- 桌面版只改了类型选择、字段和截止日输入，布局没动；桌面端没在真机 Electron 里点过，只过了类型检查

## 2026-11-04 feat(order-judge): 报价后回填结果，时间值和小时估计自动校准

**效果**：报价状态是「已报价」时，可以记客户结果：嫌贵没成交（顺手填客户说的预算）、没回音、我没接；成交了就把状态改成「已成交」，做完按新做 / 接手改分别填实际花了几小时，再点亏 / 刚好 / 值。之后打开任何草稿，报价都按回填自动校准，自用版顶上写明每个数怎么来的、依据几单：

|---|---|---|
| 实际小时 | 小时系数（乘在 AI 预估上） | 实际 ÷ 预估，取中位数 |

| 我没接 | 时间值 | 报价 ÷ 预计小时，时间值高于它 |
| 嫌贵 + 预算 | 不改价 | 同类客户预算中位数，只在自用版里给参考 |

**关键决策**：状态离开草稿时把当时的时间值和小时系数冻结进这一版，报出去的价不会因为后来的回填变掉；回到草稿才解冻

**关键决策**：同一单，网站估价用完整材料（md + 截图）得 305~479 h，把那句需求原样发给 RadQuote 得 981 h，差 2~3 倍。对照原文，客户材料里说「我改写了一版，运行报错，需要改对」，而整理出的那句丢了「已有一版」，把一个修错活放大成了重写。需求这一句本身就是估价的输入，写丢事实比估价提示词本身的偏差大得多，所以改的是评估提示词，不是估价。另外两单（Visio、净水）完整材料和那一句估出的小时本来就接近，不是普遍失真，没有改估价的输入。

```
评估 → 需求一句话（现在必含：新做 / 改造 / 修错 + 已有什么 + 规模）
        ├→ 用户复制到 RadQuote
        └→ 估价仍用完整材料（不变）
```

**验证**：用 Maxwell 的 md 跑评估 3 次，需求都带上「已有一版、运行报错、改到不报错」；用这几句话跑我们的估价，416~506 h（开发 170~222 h），与完整材料估出的 305~479 h 一致。用新需求发给 RadQuote 的结果待用户补，对照后再追加。

**边界 / 风险**：
- 需求字数上限从 80 字放宽到 100 字，历史页和手机宽度的版式没有逐一核对。
- 只在 Maxwell 一单上验证；其他单的需求写法有没有被拖长、有没有漏写「已有」，要靠后续评估观察。
- 模型有时仍会漏写已有项，漏写后的估价偏高；这是写法规则能降低但不能杜绝的。

```
开启共用 → POST /paths/merge（追加本机路径）→ 上传本机历史（只做一次）
同步：GET /sync 取正文 + 路径列表 → 只看第一条网页条目之前的路径
      → 第一个本机存在的文件 ≠ 正文 → PUT /docs/:kind（带 path，整份覆盖）
路径列表变了 → 重建父目录监听（本机不存在的目录跳过）
事件流 check → 再读一次文件交稿 → 回执；401/429/5xx 不重试，断线最多重连 2 次
```

**边界 / 风险**：找到的文件正在保存、为空或超过 1 MB 时报错，不往下一条路径找，避免把排在后面的旧文件当新稿传上去。网页里用自己的 key 时 key 只在那台浏览器里，桌面评估前需要先在网页连接一次。历史上传在共享历史满 50 条或单条超过 20 MB 时停下并报错，开关保持开启、原记录与备份保留。旧设置文件里的加密 Key 不再使用，下次保存设置时清掉。

**效果**：接单评估不再单独填 DeepSeek Key。用谁的 AI 跟随设置页「点评助手 · 写点评时用谁的」，和纱雾助手是同一份设置，默认用服务器的。评估设置弹窗只管能力档案和项目日志。设置里选了用自己的但还没填 Key 时，提示条写「设置里选了用你自己的 AI，但还没填 API key」，按钮跳到设置页。用服务器 AI 时，和纱雾助手共用每日轮次与费用额度，整单评估算一轮。同一个错误码按来源给不同文案：401 / 402 用服务器时叫用户改用自己的，用自己的时叫用户检查 Key 或充值。另外新增材料超长、今日额度用完、费用额度不够、全站繁忙、助手正在回答这几种错误提示。

**数据流**：

```
POST /api/order-judge/judge
  aiSource(uid)                    ← users.ai_config，助手同一份
  judgeConnection(uid)
    server：prepareExternal → 服务器连接
            execute = externalQuota.turn（整单一轮）
            call    = 按 estimateRequestTokens 预授权 → 调用 → 按实报结算
    byok  ：助手那条自配连接，不走项目额度
  HTTP 401/402/连接失败 → 丢掉这条连接，下次重新准备；不自动重试
```

**关键代码**：图片不能按 base64 体积估 token（一张 1280² JPEG 会估出约 55 万），预授权改按「文字按体积、图片按张」（`web/server/agent/context-provider.ts`）：

```ts
export const IMAGE_INPUT_TOKENS = 1100
export function estimateRequestTokens(body: Record<string, unknown>): number {
  const { text, images } = withoutImages(body)
  return estimateContextTokens(text) + images * IMAGE_INPUT_TOKENS
}
```

**边界 / 风险**：用服务器 AI 时，同一账号的评估和纱雾助手回合不能同时跑：后到的一方直接报 `RUN_BUSY`，不排队、不自动重试。

```ts
export function byokConnection(uid:number):{transport:ProviderTransport;model:string}{
  if(!externalEnabled('byok'))throw new AgentRunError('AGENT_AI_DISABLED',503)
  if(selection(uid).choice.provider!=='byok')throw new AgentRunError('BYOK_REQUIRED',409)

}
```
