## 2026-10-07 feat(web): 新增往期周历

**修改后效果**：番剧周历页多了「往期周历」入口，进去是独立页：先选年份（2013 年起），再选冬 / 春 / 夏 / 秋，下面按周一到周日展示那一季的海报，可以直接加追番。本季标明「还在跟着周历更新」；接入前的季度第一次点开要等几秒（约 10 秒）现翻，之后永久存下、秒开，页面注明是按首播日翻出来补的。翻失败会如实显示原因，不自动重试。

**关键决策**：
- BGM 的 `/calendar` 只返回当前在播的番，过季就掉出去，没有往期周历。所以从接入起每季存一份 BGM 周历原样的快照：`$DATA_DIR/calendar-seasons/YYYY-MM.json`，永久保留，不进部署目录；本季内每次拿到新周历按 bgmId 取并集并入（同一部以最新的星期和资料为准，中途完结掉出周历的番不丢），季度一换自然冻结。季度按东八区算。
- 服务端周历缓存从 14 天缩到 7 天（前端同步），本季内的新番和改星期才能每周被收进来；刷新只由用户访问触发，没有后台定时探测。进程启动时已落盘的周历也会补进它所属季度。
- 接入前的季度走「按首播日翻」：BGM 按年月检索接口命中首播日在该季首月的条目，一页 50 条分页取完；该接口的 `platform` 参数无效，只能自己按字段筛，保留 TV + WEB，与 BGM 当季周历收录范围一致（实测 2026 年 10 月季：周历 100 部在检索结果里，其中 TV 80、WEB 20）。星期由首播日（日本当地日期）推算，实测和当季周历对上 100 部里的 98 部。补出来的快照标 `derived`。
- 补季度只在用户点开时触发：同一季只补一次（共享在途请求），所有季度的 BGM 请求排成一条串行队列，不会因连点并发打 BGM；补成功才落盘，失败不存半成品。当季只靠周历快照，不倒推；最早到 2013 年第一季。
- 预热脚本 `npm run warm:seasons`（`web/scripts/warm-calendar-seasons.ts`）：部署后在服务器上跑一次，把 2013 年起没翻过的季度从新到旧翻完，约 20～30 分钟。限流预防：串行；页与页间隔 2.5 秒、季与季间隔 10 秒，各带 ±15% 随机抖动，可用 `--page-gap` / `--season-gap`（毫秒）放慢；任何一次失败（429 / 403 / 5xx / 超时）立刻整体停下，不重试、不跳过继续打，已翻好的季度已落盘，稍后重跑从没翻过的接着来。`--limit N` 先试几个，`--dry-run` 只列清单。数据目录跟服务一致，服务在跑也能跑（落盘原子）。
- 新接口 `GET /api/calendar/seasons`（列表，含未补的季度）和 `/api/calendar/seasons/:key`（单季，缺失的往期季度现补）。已登记进 Agent 功能清单。
- 海报上「追 / 取消追」逻辑从周历页抽成 `useTrackToggle`，周历页和往期页共用。

**边界 / 风险**：
- 补出来的季度只含「首播日在该季首月」的番：前一季接着播的番、晚一两个月才开播的番都不在内，星期偶尔差一天；2026 年 10 月季里有 2 部周历有而检索没有，另有 2 部星期对不上。
- 本季和接入后的季度取决于有人访问周历的时间点；整季没人访问就没有快照，之后也只能靠「按首播日翻」那套近似。
- 季度交替的前几天，上一季没完结的番会被并进新季度快照，之后不会自动清掉。
- 一次现翻对 BGM 发约 3～4 个请求，用户点开不会等间隔，只靠串行队列；部署后建议先跑一遍预热脚本，免得真人逢新季度都等。预热脚本只在本地测过 2 个季度和一次失败即停，没有跑完全部。
- 只在本地验证了桌面和手机宽度的显示、合并与时区的脚本，以及补 2019 年春季、2024 年秋季、2013 年冬季；没有线上实测。

## 2026-10-07 feat(web): 追番页新增按年份和季度排列

**修改后效果**：追番页视图切换由「卡片 / 列表」变为「卡片 / 列表 / 时间线」。时间线按加入追番的时间归到年份，再分冬（1 月）、春（4 月）、夏（7 月）、秋（10 月）四季，每季一张贴了和纸胶带的纸卡，番名是小贴纸：没看完的是粉色虚线，看完的是实线加对勾。观望的番不算追番，不进时间线；搜索、标签、状态筛选在时间线里照常生效。点番名打开编辑弹窗，新增「记在哪一季」，可以手动挪到别的年份和季度，挪完有纱雾口吻的提示。页面文案、空状态均为和泉纱雾的语气。

**关键决策**：
- 原来没有创建时间，只有每次编辑都会刷新的 `updatedAt`，不能拿来归档。新增 `tracks.created_at` 列（`server/db.ts`），只在插入时写入，编辑、同步更新都不动它；老记录用 `updated_at` 回填一次（偏晚，用户可在弹窗里改）。
- 接口返回 `createdAt`；`PUT /api/tracks/:bgmId` 接受 `createdAt` 用于手动挪季度，必须是正整数且不晚于当前时间。挪季度时落在该季度首月 1 号中午，避开时区边界。
- 前端对没有 `createdAt` 的本地旧缓存退回 `updatedAt`，归档逻辑集中在 `src/tracks/TrackTimeline.tsx`。
- 只归档动画；漫画、小说本来就不在网页版追番页里展示。

**边界 / 风险**：
- 从 Bangumi 导入的番，创建时间是导入那一刻，不是用户当初收藏的时间，需要的话手动挪。
- 备份恢复不带创建时间：恢复到新账号时每部番按备份里的最后修改时间归档；已存在的番保留原创建时间。
- 桌面端同步新增的番，创建时间取客户端的最后修改时间（夹到当前时间以内），不是真实加入时间。
- 只在本地用测试账号验证了桌面和手机宽度的显示与挪季度，没有线上实测；纱雾台词为按角色性格撰写，未经反复打磨。

## 2026-10-08 fix(web): 补回加番后缺失的封面

**复测结论**：10 月 7 日的封面代理缓存改动没有解决这次“我的追番”加番缺图。已登录的本地测试账号中，四张缺图卡片的 `cover` 字段为空，页面没有发起图片请求。用户提供的终端日志未见 429，也没有触发 15 分钟停发；日志里两次 15 秒超时是 `/r/400` 取图请求，不能用来解释这四张卡

**原因与改动**：加番后异步获取 Bangumi 条目详情以补封面，原先只随机延迟 0.8～2 秒，连续加番仍会并发请求；失败被静默吞掉。现在详情补全与封面取图共用队列，最多同时进行 2 个上游请求，相邻请求至少错开 1 秒；收到 429 后停发尚未发出的封面请求，不自动重试。失败原因写入服务端终端。读取追番列表时，仍缺封面的旧条目会排入一次补全。系统补图另增网页视图版本，让页面重新读取封面；桌面同步用的 `tracks_rev` 不因补图变化

## 2026-10-07 fix(web): 修复一次加多部番时封面整批加载失败

**修改后效果**：一次加十几部番，封面不再整批变灰块或裂图。每张 BGM 封面只向图床取一次，取到后存进服务器磁盘，之后（含重启、重新部署后）直接从磁盘返回，不再碰图床。

![封面代理缓存](../devlog-assets/web-cover-proxy-cache.svg)

**关键决策**：
- 原因是封面代理 `/api/cover/*` 没有缓存也不限并发：浏览器同时要十几张，服务器原样同时打到 `lain.bgm.tv`，图床对服务器 IP 限流，整批失败；失败不缓存，刷新又是新一轮并发，所以越刷越不好，过几小时限流窗口过去才恢复。这是根据症状的推断，没有抓到线上的上游状态码。
- 取图逻辑抽到 `server/bgm/cover-proxy.ts`：磁盘缓存（`$DATA_DIR/bgm-cover-cache`，在部署目录外）→ 同一张在途请求共用 → 最多 3 个并发、排队上限 80（超出 503）→ 整张读完才写盘（先写临时文件再改名）。
- 不做应用层自动重试，失败原样返回具体原因（上游 HTTP 状态、类型不符等）并打日志，符合 AGENTS 对限流的规定。
- 磁盘缓存不设过期：封面地址带图片内容哈希，图换了地址就变。

**边界 / 风险**：
- 上线时已经被限流的封面，要等限流窗口过去才第一次取到，之后才不再受限流影响。
- 磁盘缓存只增不清，每张约 200KB；追番数量增长时需要留意 `bgm-cover-cache` 的体积。
- 在途去重和排队名额在进程内存里，重启后清零，多实例各算各的。
- 只验证了脚本层：同一张 3 个并发请求只去图床 1 次，第二次约 1 毫秒从磁盘返回。没有在浏览器和线上实测。
- 前端 `coverUrl` 未改；百科旧封面经 `/api/subject-cover/:id` 重定向后同样走这条代理。

## 2026-10-04 perf(web): 优化追番列表加载和手机搜索体验

**效果**：我的追番首次加载时先显示已收到的卡片，其余条目继续传输；已有完整缓存时先显示缓存，再校验版本。加番搜索在中文选字结束后才发请求，改词、清空或关闭弹窗会取消旧搜索，旧结果不能覆盖新词；重复点击当前搜索页签也不会再永久转圈。2026-10-03 的 iPhone Chrome 真机验收中，5 次搜索从停手到结果进入页面为 390～569 ms，用户确认「已经可以算是解决问题」

![追番加载、搜索与异常边界](../devlog-assets/tracks-loading-search-flow.svg)

**关键决策 / 数据流**：

- **列表分批接收，页面分批展示**：首次无完整缓存时采用 NDJSON 快照，首批最多 18 条并携带完整分类计数，后续继续发送；响应显式设置 `X-Accel-Buffering: no`，避免上线后被 Nginx 攒成整包。页面先渲染 18 张卡片，滚动时继续增加展示数量；传输顺序通过条目索引还原，不把首批计数冒充完整列表计数
- **半份列表不进入完整缓存**：只有收齐并校验通过的快照才保存。中途断流保留已显示内容，显示已加载数量和「继续加载」；尚未收齐时，筛选未命中也不能宣称列表中没有这部番。加载中发生修改会中止旧流，重新取得服务器确认的新快照，避免旧数据覆盖刚改的进度或标签
- **搜索保持完整结果与既有排序**：默认只查服务器离线索引及共享补充库，只有用户点击「在线搜 Bangumi」才访问在线搜索。输入保持 300 ms 防抖，拼音组合期间不发送关键词请求；取消请求之外还保留请求代次校验，防止晚到结果回写。搜索仍一次返回整批候选，按原有年份规则排序，不照搬追番列表的分批追加策略
- **失败要有明确终点和原因**：响应头与响应体共用请求截止时间，保留断网、超时及服务端错误原因，提供手动重新搜索；429/5xx 不自动重试，也不伪装成零结果。登录状态读取失败不直接广播退出，仅明确的 401 清除登录身份。超时保护负责结束等待，不作为搜索提速的证据
- **减少片源前置等待，避免缓存残缺图片**：稀饭未绑定及重新绑定直接进入搜索；已有稀饭 / Girigiri 绑定直接返回，不先等待周表。封面仍由本站代理，完整读完图片字节才返回成功缓存头，并更新封面缓存版本。同步调整手机端相关弹窗的布局
- **把浏览器阶段落到服务端日志**：按请求 ID 关联服务端处理与浏览器等待响应头、读取响应体的耗时；搜索补充输入等待、排序及 React DOM 提交计时，快速样本也上报，便于和慢样本比较。被用户取消的旧搜索不再记成失败；日志不只留在浏览器控制台。

![iPhone 搜索实测及状态文案](../devlog-assets/tracks-loading-search-evidence.svg)

**边界 / 还未确定的部分**：本轮真机体验与日志支持问题已解决，但前后不是网络条件严格一致的受控对照，尚不能拆分减少拼音请求、服务重启、网络状态及浏览器连接状态各自的贡献。此前的数秒等待集中在响应等待与接收，不能据此认定离线数据库规模或渲染是根因，也不能把全部改善归功于某一项改动。搜索现已整批返回且使用顺畅，未再增加渐进搜索或自动重试机制
