## 2026-11-14 fix(web): 修复集名认不出回转详情页

**修改后效果**
- Girigiri 把先行放送的第一集标成「先行01」时，原来认不出集号，第 1 集从选集里消失，「跳去源站看」直接显示 `GIRIGIRI_EPISODE_NOT_FOUND` 的 JSON；现在「先行01」「先行版 01」「先行放送01」都认作对应集数，在线播放和跳源站一起恢复
- 更怪的集名（如「抢先看第一话」）也不再从选集里消失：按它在列表里的位置补集号，只在这个号空着时才补，选集格子里显示原集名；例如「抢先看第一话、02、03」会排成第 1、2、3 个，而「PV、01、02」里的 PV 仍不列出
- 「跳去源站看」时源站确实没有这一集，或遇到其他认不出的集名，改为跳到该番的 Girigiri 详情页让用户自己挑集，服务端终端记一行是哪部番哪一集

**边界 / 风险**
- 只放宽了「先行」前缀；其他认不出的集名靠位置补号，排在正片之后的 OVA、SP 会出现在列表末尾、以原名显示，但仍占一个集号，追番进度如果走到那个号会打开它
- 在线播放页缺集时仍显示播放器自己的错误提示，没有跳详情页：页内本来就有选集列表可以换

## 2026-11-10 fix(web): 服务器预取下一集改为播到 70% 后再预取

**修改后效果**
- 只打开播放页、没往下看的人，不会再让服务器白下一整集（单集最大 1.5GB）
- 播到（或拖到）70% 时，播放页向服务器发一次请求，服务器才登记下一集预取；之后的排队规则不变：正在看的集优先，空闲了才下预取，每人只留一个
- 真在连看的人照旧：一集 24 分钟，70% 约 17 分钟，离看完还有 7 分钟；服务器从源站下一集实测约 5 分钟（跟观众的网速无关），点下一集时通常已经在服务器硬盘上
- 没下完也不从头来：下一集一打开就升为「正在看」最优先，已下的块直接用、缺的加急拉，等于退回不预取时的边下边播

**关键决策**
- 不合 PR #10（直接删掉预取）：那样所有默认用户点下一集都要现拉；这次只把触发时间从「打开页面」挪到「看到 70%」
- 去掉原来的 30 秒延迟：那是挂在「打开页面」上时用来滤掉只点开看看的人，现在触发点已是 70%，再等 30 秒只会让只看到片尾就切走的人错过预取
- 只发一次、不心跳、失败不重试：失败的代价只是下一集现拉，不值得多打请求
- 正在用胶片柜本地缓存播放时不发：下一集由胶片柜自己下
- 胶片柜取下一集地址（`/playlist?ep=N+1`）时服务器仍会顺手开始下那一集，保留：弱网时胶片柜会让带宽给播放、甚至退回经本站播放，这时服务器那份能接上

**边界 / 风险**
- 没在真机 / 浏览器里实测过 70% 触发和起播时间
- 看到 70% 就关掉的人仍会让服务器下一整集

## 2026-11-09 fix(web): 修复切回页面后本机已缓存的一集报「这条线路播放出错」

**修改后效果**
- 本机已下完的集，续播时切到后台再回来，不会再被当成「seek 卡死」整个换成经本站；回来后接着从本机播
- 就算真要退回经本站，也用开播时解析出的真线路，不会再请求一个播不了的地址、每 1 秒报一次 code=4

![本机已缓存的一集切回页面报播放出错：后台时间被当成 seek 卡住](../devlog-assets/web-local-cache-hidden-seek.svg)

**关键决策**
- 真机日志（11-08 20:37，iPhone，第 5 集）：本机挂载续播 1065.7 秒，用户切走 16 秒，回来时看门狗按 `seekAt` 起算已超过 8 秒，判定 seek 卡死，`ahead=Infinity`（整集在本机）也照切；退路用的线路是本机缓存的 host+路径，没有 `s` 也没有协议，经本站请求必然 code=4，之后每秒重试一次。从放映室直接点开没续播位置，不触发 seek 等待，所以没事
- 修两处：后台时看门狗不累计 seek / 卡顿时间，回前台重新起算；`serverOf` 在线路没有 `s` 时改用开播时解析的线路，解析不到就报「本机文件读不出来」而不是空转
- `scripts/check-playback.sh` 新增第 2、3 个参数，可按正则看某一集挂载、续播、切换的完整经过

**边界 / 风险**
- 没在真机复测；seek 到 1065 秒本身会不会慢，日志里看不出来（同一集随后不带续播位置重开，正常）
- 真正的 seek 卡死（前台、整集在本机）仍会在 8 秒后切到经本站，这是原有的兜底

## 2026-11-03 feat(web): 退回经本站播放后继续缓存

**效果**：本地缓存播放退回经本站（或换到不能本地缓存的线路）后，这一集照样下进本机，下完接着下一集，但让着播放：暂停时一直下；播放中缓冲领先满 60 秒才下，掉到 20 秒以下就停。源站拒绝过本机的不再下

**关键代码**：`page.ts` 的 `governBg` 挂在每 0.5 秒的卡顿看门狗上，开关之间隔开两个门槛免得来回切；停就是中止当前连接，再开从盘上缺的块续下

```js
var want = idle || ahead >= (bg.on ? 20 : 60)
```

**还存在的问题**：

- 页面关掉或 iOS 切到后台下载就停，只有亮着屏暂停时能补完
- 播放中浏览器自己的缓冲常常到不了 60 秒，慢网络上基本只在暂停时下

## 2026-11-03 perf(web): 缩短本地缓存播放 mp4 的起播等待

**效果**：

1. 本地缓存播放 mp4 时，起播前只拉开头一块和目录（moov）所在的那几块；目录在开头的文件不拉结尾。乱马 ep4 起播约 4 秒（11-03 iPhone）
2. 目录在结尾时，手机直连源站和本站同时送这几块，先到的那份存进手机就起播，晚到的丢掉；整集仍由手机直连源站下载
3. 直连传输中断的日志带上起始块、已收字节和耗时，分得出「首字节都没等到」和「中途断开」

![本地缓存起播：只拉目录所在的块，本站同时送一份](../devlog-assets/web-local-cache-tail-race.svg)

**关键代码**：

- 目录位置从第 0 块的盒子表读：`mdat` 结束处就是结尾目录的起点（`media-cache-worker.js` 的 `moovStart`），读不出来才按 4 块盲拉

  ```js
  if (type === 'moov') return -1
  if (type === 'mdat') return at + size < total ? at + size : null
  ```

- 本站送的是整块，不只是目录：播放器要结尾时会往前取整（本机 Chrome 从目录前 7.5KB 起要）。`tailBlocks` 把缓存的目录减回前移时加的偏移，块边界到 `mdat` 末尾那段现拉；下载器收到后按普通块落盘，并中止正在拉结尾的直连

  ```ts
  const tail = await tailBlocks(media.url, layout, Number(c.req.query('from')))
  ```

**还存在的问题**：

- 每集起播从本站多拿约 1.6MB；本站拿不到时只等直连，两路都没到仍是约 18~22 秒报错后换到经本站播放
- 直连拉结尾断开时本站那份能不能顶上，真机还没遇到：11-03 直连很快（15.1Mbps），没有断开
- 源站本身跟不上码率时起播仍慢，播放前不判断快慢

## 2026-11-02 fix(web): 修复拖动进度条误切退路并退出全屏

**效果**：

1. 本地缓存播放时拖进度条（跳 OP、跳到 ED、连拖几下）不再被当成「下载变慢」切到退路；跳到还没下的位置，iPhone 约 2.5 秒出画面（乱马 ep2）
2. 下载确实跟不上、需要切退路时，全屏不退、从原时间点接着播，切换那几秒停在原来那一帧上，不再像整页刷新、进度归 0
3. 索引放在文件末尾的 mp4（夜樱 ep19）在 iPhone 上起播不再 20 秒后报错退回

![拖进度条不再被当成「变慢」切走](../devlog-assets/web-local-cache-seek.svg)

![真要切退路时：停在原画面，全屏和位置都保留](../devlog-assets/web-local-cache-swap.svg)

**关键代码**：

- `page.ts` 的 `watchSlow`：`seeking` 到 `seeked` 之间（`seekPending`）不看领先量趋势，只看等了多久；上限 `seekWaitMs()` 按下载器实测速度估一块的时间 ×2 再加 4 秒，限 8~60 秒
- `media-cache-worker.js`：`CHUNK` 4MB → 1MB；新的 `need` 排最前、远处的旧 `need` 作废；起播先把尾部 `TAIL_CHUNKS`（4 块）整段拉完，再按块延伸 Range
- `page.ts` 的 `swapSource`：自动退路不再 `mount`，同一台 ArtPlayer 只换 `art.url`，`loadedmetadata` 后跳回原位置；挂在 `<video>` 上的监听改认 `art === me`，HLS 的 `customType` 按调用时的 `cur` / `generation` 取值。换前 `freezeFrame` 把当前帧截成 `poster`，`playing` 后撤掉

**还存在的问题**：

- iPhone 全屏是系统播放器，切换时会不会显示定格的那一帧未真机验证；不显示就是黑一下（11-02 实测约 4.7 秒）
- 跳到还没下的位置仍要等一整块 1MB 落盘，1.8Mbps 约 4.5 秒
- 旧格式（4MB 一块）没下完的缓存会整集重下一次；手机上可能还缓存着旧的 SW / 下载器，要关掉标签页重开才生效
- 换集、手动换线路仍整台重建播放器，会退出全屏

## 2026-11-01 fix(web): 修复 iPhone 本地缓存播放器异常

**效果**：iPhone（单连接约 1.8Mbps）上本地缓存播放约 10 秒出画面，整集存进手机，下完自动接着下下一集。改前一直不出画面，约 40 秒后退回原来的播放方式，只存下 8MB，下一集也不会下

![iPhone 上本地缓存起不来：结尾那一小块排到了整集后面](../devlog-assets/web-local-cache-ios-tail.svg)

**关键代码**：10-30 写的下载顺序是「第 0 块 → 最后一块 → 其余」，但每次开流时会把 Range 一路延伸到后面所有缺的块，从第 0 块开的那条请求就是整集，最后一块根本排不上。现在最后一块到手前每次只拉一块（`media-cache-worker.js` 的 `run`）：

```js
let end = start
if (state.have.has(n - 1)) while (end + 1 < n && !state.have.has(end + 1)) end++
```

**还存在的问题**：Safari 第一次请求要等整块 4MB 落盘才有首字节，11-01 实测 5 秒，10-31 那次 19 秒；手机更慢、逼近 WebKit 约 18 秒的等待时，这里会先出事

## 2026-10-30 feat(web): 新增本地缓存播放器

**效果**：

1. 在线播放时，浏览器用本机网速直连源站把整集下到本机，播放器读的就是这份正在写入的本地数据，播放和下载只拉一份流；这一集下完立刻接着下下一集，下载不受暂停影响。稀饭新番主线-2、备用-1 和 Girigiri 的 mp4 / HLS 线路都覆盖；稀饭新番主线-1 浏览器读不到，照旧经本站
2. 开播先看本机有没有下完这一集：不管是哪条线路、稀饭还是 Girigiri 下的，同一部番（同站同番，或同一个 Bangumi 条目）同一集就直接播本机那份。整集下完后起播和跳转都在 0.1 秒内
3. 本机没有时自动挑线路：按全站用户实测的源站速度，第一条已够 6Mbps 就直接用，不够才换明显更快的（字幕不同也换，只要是同一集）
4. 播放中下载跟不上时，切到画面完全一致的退路（同一个文件的其他线路，或同一条线路改走服务端），从当前时间点、保持播放 / 暂停接着播
5. 看过的集默认保留 30 天（从最后一次播放算），标了「鉴赏神回」的不清。设置 →「本地缓存」按标题 + 集数列出已缓存的集，显示大小、剩余天数和已用空间，可直接播放、手动删除
6. 断网或本站连不上时，下完的集照样能打开、播放、跳转，并在已下完的集之间切换

![开播时自动挑线路：按全站用户实测的速度](../devlog-assets/web-local-cache-line-pick.svg)

![播放中变慢：切到画面完全一致的退路](../devlog-assets/web-local-cache-slow-switch.svg)

**各源站能不能直连**（10-30 本机经代理实测，速度只作相对参考；现在由页面自动判断）：

| 线路 | 源站 | 格式 | 浏览器能否直连读 | 下载方式 |
|---|---|---|---|---|
| 稀饭新番主线-2 / 旧番主线-1 | play.xfvod.pro | mp4 | 能（单连接 20.5Mbps） | 单连接顺序拉 4MB 块 |
| Girigiri | akua.girigirilove.com | HLS | 能（单连接 9.8Mbps） | 同时拉 4 片：一片 0.2~2MB、首字节 1.5~4 秒，一片一片拉只有约 2Mbps |
| 稀饭备用-1 | dl.playxf.top | HLS | 能（单连接 1.5Mbps，6 连接 23.6Mbps） | 一片按 Range 拆 6 段并发 |
| 稀饭新番主线-1 | apn.moedot.net → 联通网盘 | mp4 | **不能** | 网盘见到 Origin 头就 403，浏览器跨域读一定带 Origin |

**数据流**：

```
播放页 ──job(当前集)──▶ 下载 Worker ──直连源站──▶ 源站
                            │ mp4：每满 4MB 写一块 <序号>.bin；HLS：整片到手写 r<序号>，播放表改写成 index.m3u8
                            │ 写完、flush、close（HLS 先写临时名再改名）之后才广播「到了」
                            ▼
                     OPFS media-cache/<sha1(host+路径)>/
                            ▲
播放器 ──/media-cache/<hash>（mp4，按 Range）或 /media-cache/<hash>/index.m3u8（HLS）──▶ Service Worker
                     缺的块 / 片先发 need 让下载器插队，再等广播

下载器每 5 秒的实收速度 ──POST /api/player/line-speed──▶ 服务端 data/line-speed.json（全站一张）
服务端解析出的「稀饭线路 N → 源站」也记进同一张表；播放列表顺带返回各线路的全站速度
```

- 切块 / 按片存，而不是一个大文件：同步写句柄独占文件，SW 在它打开期间读不到；按块写完关闭再广播，读取端只会看到已落盘的字节
- mp4 先下第 0 块和最后一块（moov 在尾部的不用等整集），其余顺序拉；跳进度离当前下载位置超过 3 块就断开重开到目标位置。HLS 从播放器要的那一片往后接着拉，到尾再回头补
- 身份按 host + 路径（不含签名），签名换了也认得出同一集；mp4 总长 / HLS 片数和本地记录不一致就整集重下，防串片
- 重试预算只有一份：HTTP 错误直接失败不重试；只有传输中断（含 20 秒没收到数据）才续传，全集共用最多 3 次，间隔 2/6/15 秒加抖动。失败时同线路退回原来的方式，本页不再用本地缓存
- 换线路时先销毁播放器，再让下载器中止旧任务、开新任务；换集是整页跳转，Worker 随页面结束，进新页从盘上已有的块 / 片续下
- 速度表按源站记，每个源站留最近 50 个用户、每人一格（自己的值按新样本 3 成滚动），取九成位置的值，永久保留；只收服务端自己解析出过的源站，每人 4 秒最多收一个样本。只记稀饭：Girigiri 所有线路在同一个源站
- 「这台设备不能直连某源站」只记在本机 localStorage，7 天后再试
- 离线：SW 把播放页和它的脚本、样式、字体按「先网络、失败才用副本」存一份（最多 60 个播放页）。没开过的集借最近一次的播放页，只换页面参数（和服务端同样校验 src / id / ep）
- 下载日志、测速被拒、本机命中等经播放页的 client-log 回服务端终端

**边界**：

- 页面关掉下载就停，下次打开续下；iOS 切到后台会挂起；Safari 7 天没打开的网站数据可能被系统清掉，iPhone 上 30 天保留只能尽量做到。iPhone 真机尚未验证 Safari 的 <video> 和原生 HLS 请求是否经过 SW，不经过时会出错并退回原方式
- SW 还没接管播放页（第一次打开网站、隐私模式）或没有 OPFS 时完全走原方式；剩余空间不够时不下（mp4 按整集 + 64MB，HLS 按第一片估算）
- 本机到源站带宽低于码率时只能部分缓解；网络抖动连续中断 3 次后这一集不再下
- 没人看过的线路一直没有速度数据；全站速度和某个运营商下的实际速度可能不一致，分错时靠播放中切换兜底
- 同一文件线路之间切换、「领先不到 30 秒就备、不到 10 秒就切」都还没在真实环境触发过：测试用的番里没有两条线路是同一个文件，几次真实变慢都是直接卡住
- 不同压制版本（Girigiri 繁中 260 片 / 1426.0 秒、简中 294 片 / 1420.1 秒）同一时间点画面差几秒，一集中途不切过去
- 本机已下完的那份坏了：先等最多 45 秒（SW 等缺的块），再回到正常挑线路
- 切换会重建播放器，画面黑一下；退到服务端吃服务器出口（约 6Mbps，约够 2 人同时看），这一集的本地下载会停掉；一次页面里每条线路只会被切走一次

## 2026-10-12 fix(web): 修复稀饭 iPhone 跳转进度后无法起播

![稀饭 iPhone 跳转进度后起播慢：三种卡法与三条规则](../devlog-assets/xifan-seek-start.svg)

**效果**：跳转到还没下载的位置（拖进度条或「跳到上次进度」），服务器按真机请求顺序用真实源站回放：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 跳到上次进度，起播要的三段到齐 | 15.1 秒（真机 21.7 秒） | 6.2 秒 |
| 拖进度后，「回补旧位置」的请求 | 把下载拽回旧位置十几秒 | 不再抢下载位置 |
| 拖进度后往后播放，60 秒到手 | 39.9MB | 49.1MB |

更早一版（66 秒才回第一个字节、画面停在 5:36）的成因也在这里：插队的块被游标挪动反复中止。

**原因与规则**（`web/server/xifan/disk.ts` 的 `GAP_BYTES` / `READAHEAD_BYTES`）：

```text
iPhone 跳转后：64KB → 等回来 → 下一个 64KB → 等回来 → 中间漏的 832KB    一环等一环，每环都要现下一块（约 5 秒）
               跳转点往后（读到文件末尾）
拖进度条还多一个：从旧位置回补到跳转点（5MB → 116MB）

规则 1：读到文件末尾的请求 = 正常播放，只有它挪下载位置
规则 2：有终点、离终点 ≤4MB 的请求 = 补洞，连同其后 1MB 插队一起下（4 块并行，一轮到齐），插队块不被挪位置中止
        离终点更远的（回补旧位置）不插队、不挪位置，等顺序下载顺路带上
```

faststart 把「读到虚拟文件末尾」也按「读到末尾」转给盘上缓存（原来会变成有终点的区间），否则规则 1 认不出播放请求。

参考：libtorrent 流媒体按播放位置给后续块设截止时间（<https://www.libtorrent.org/streaming.html>），rclone 的 `--vfs-read-ahead` 读不到时连同其后一段一起取。

**边界**：

- 跳转起播仍要等一块（256KB）从源站下完，约 5~6 秒；更短要把块拆小，没做
- 这集码率 2.3Mbps，服务器从源站拉约 5.4Mbps，往后播放余量约 2 倍；码率再高或多人同看时余量更小
- 服务器每 5 秒打一行 `[xifan:disk] … 进度`（入口速度、下载位置、各请求的位置和领先），只在有集正在被看时打

## 2026-10-06 fix(web): 修复PC网页播放起播后反复卡顿

**效果**：

1. 稀饭 mp4 点开就由服务器 12 条连接按顺序整集下到盘上，播放器要哪段从盘上答；源站合计速度高于码率时，起播后一路不卡，往回拖、拖到已下过的位置即时
2. 拖到还没下的位置：12 条连接全部转去新位置（旧位置在飞的块当场中止），攒够 1.5MB 连续数据再出第一个字节，之后不再卡；VPS 实测死神 39 集（311MB）拖到 11:40 等约 10 秒，之后一路顺
3. 整集下完后再打开 / 换签名重开都直接用盘上那份，目录（moov）也从盘上读，播放按钮不再等源站
4. 下一集预取共用同一套下载：只在没有「正在被看且没下完」的集时才拿连接，当前这集下完（实测一集约 5 分钟）之前完全不动；每人只保留最新一个预取，换番即撤

**原因**：2026-10-06 VPS 实测源站单连接只剩约 57KB/s（12 路合计约 650KB/s，这集码率约 154KB/s），512KB 一块要 9 秒、完成顺序乱。旧的内存滑窗在开头为了快起播不设闸，第一块一到就开播、下一块晚几秒才到，就是「播 1~2 秒卡几秒」；拖进度后的闸最多等 6 秒同理。不是修移动端引入的。

```text
/playlist ──▶ warmDisk：探长度，12 路从 0 起拉 256KB 块 → DATA_DIR/prefetch/<身份>.mp4.part
/stream ──▶ faststart 映射 ──▶ serveFromDisk
              │  整集在盘 ─────────────▶ 直接读文件
              │  大 Range（新位置）────▶ 挪游标、中止别处在飞的块 → 等「连续 1.5MB」(≤20s) → 边写边读
              │  小 Range（≤1MB 探测）─▶ 只插队要那几块，不挪游标
下载优先级：正在被看的集（2 分钟内有读取）> 预取的下一集
```

**关键代码**：

- 媒体身份去掉签名参数（`disk.ts mediaKey`）：签名一换就当新文件的话，整集在盘也会重下一遍（测试实测第 40 集重开又「开始落盘 174MB」）。换签名后第一次复用在后台核一次总长度，对不上删掉重下

```ts
export function mediaKey(url: string): string {
  const u = new URL(url)
  return u.host + u.pathname
}
```

- 只有最新的大 Range 能挪下载游标（`latestReader`）：PC Chrome 拖进度后旧连接还挂在旧位置等数据，两边都能挪游标就来回抢，新位置攒不起领先
- 重试预算一份、按时间算：4xx/5xx 立即整集作废并把原因交给播放器；传输中断的块冷却 3 秒换连接再拿，连续 60 秒一块都没成才判源站不通（`TRANSPORT_GIVEUP_MS`）

**边界**：

- 拖到未下位置的等待由源站速度决定（约「一块的耗时 + 攒 1.5MB」）；源站合计速度低于码率时仍会卡，这是物理下限
- 服务器 → 观众还受 VPS 出口约 6Mbps 限制，整集在盘时拖进度画面动起来也要 2~5 秒（测试经 SSH 隧道实测）
- 未完成的 `.part` 不跨重启（「哪些块已到」只在内存）；超过 1.5GB 或探不到长度的文件仍走 `stream.ts` 内存会话
- 旧预取按整条 URL 哈希存的文件认不出来，按 4GB 回收目标自然淘汰

## 2026-10-03 fix(web): 修复移动端站内播放稀饭动漫不起播

![iPhone 看稀饭新番一直转圈的原因与修复](../devlog-assets/xifan-web-moov-tail.svg)

**效果**：iPhone Chrome 在站内看稀饭新番（实测 Re:Zero 第四季 夺还篇）起播约 3~5 秒、全程不卡；拖进度后从新位置续拉，起播后不再二次卡顿。目录本来就在文件开头的旧番原样透传，不受影响

**原因**：这一季的 mp4 把目录（moov）放在 730MB 文件的末尾，上一季在开头。手机没有目录解不出任何一帧，得先单独去文件尾拉 2.4MB，这条请求还要跟服务器已开的 12 条下载连接抢约 5Mbps 的入口。播放地址本身没问题：用的是新站 `issue-web-playback`，和官方播放器同一个 `fallback` 请求

**关键决策**：

- `web/server/player/faststart.ts`：目录在尾部时，服务器把尾块只拉一次，给 `stco/co64` 里每个块偏移加上尾块长度，放到 mdat 前从内存答；其余区间偏移减尾块长度，映射回原文件，底下照旧走预取盘 / 12 路会话。文件总长不变，拖动位置一一对应。拉 playlist 时就在后台拉尾块
- 底层会话不认 Range 终点、总吐到原文件末尾，也就是已经挪走的尾块，所以映射层要按长度截断。透传分支交出的是 undici 的 Node 流（只是类型写成 Web 流），要先 `Readable.toWeb` 再读。第一版没转，真机拖进度时抛错，留下一条没人消费的上游响应；源站断开连接时进程崩溃，手机只收到成片 502
- `web/server/xifan/stream.ts`：区间没有读取端要持续 15 秒（`ABANDON_GRACE_MS`）才收。iPhone 拖进度后会断开、去文件开头补一个小请求，几秒后在原位置附近重连。原先「没人读、别处有人读就立刻收」会丢掉刚攒好的区间，实测跳到 17:51、到 18:00 卡一下
- `/api/player/stream` 每条请求结束打一行 `[player:req] range= status= first= sent= end=`，用来还原手机的请求顺序，在本机按同样顺序重放复现（`docs/web/网页移动端问题复现调试通用指南.md`）

**边界**：

- 服务器入口约 5Mbps（6M 宽带跑满；去测与稀饭无关的测速站也是 685KB/s，不是被源站限速），这集码率约 2.2Mbps，一个人看约 2 倍余量；预取下一集共用这条入口
- 拖到服务器还没下载的位置时，第一下要等源站送来新位置的数据，实测几秒到十几秒
- 解析失败时 60 秒内按原文件透传；`stco` 加偏移溢出 32 位时同样放弃改写
