# 网页版播放页重写方案

> 意图见 [`docs/intent/播放页重写.md`](../intent/播放页重写.md)。本文是方案，未动代码。

## 一、旧页为什么救不了

```text
旧页（server/xifan.ts 2092 行 + girigiri.ts 500 行）
  boot → playlist → playLine
    ├─ needsProxy? ──否──→ <video> 直连源站 ──失败/饿死──┐
    │                                                  ▼
    │                                        probe → buffer gate → rescue（悄悄改走服务端）
    │                                                  │ 切 src 时 <video> 被重置 → 进度回 0
    └─ 是 → 慢源名额(admission) → 预转 HLS(ffmpeg) → 起稿浮层 → 轮询 …
                                                       │ 任何一环失败
                                                       ▼
                                             embed 官方 iframe（广告页）
```

Sentry 里 11 个 issue 就是这条链在 iOS 上逐环触发的记录。每一环单看都有实测依据，
合在一起就是「四条路径 × 三种回退 × 桌面/触屏两套判据」，没有人能预测某一次点击会走到哪。

## 二、新页：一条路

```text
播放页(新)  ──/api/player/playlist──▶ 解析层(不动：xifan/resolve.ts、girigiri/resolve.ts)
   │
   └─ <video> / hls.js  ──只认──▶ /api/player/stream?u=   (mp4，沿用 stream.ts 分片核心)
                               /api/player/hls?u=      (m3u8 改写后转发，分片同样经服务器)
```

- 前端**没有**直连、探测、救援、iframe。失败就是失败：显示原因 + 「重试」按钮，不自动换线。
- 稀饭 / girigiri 共用同一张页：解析层输出统一成 `{ source, kind: 'mp4'|'hls', url }`。
- 慢源名额（slow-playback）、预转（prepare.ts）**不接入新页**。模块先留着不删，等新页稳定后再清。

### 播放器

用成熟库（候选 **ArtPlayer**，自托管到 `/api/player/vendor/`）：手势拖动、双击、倍速、进度记忆、
缓冲态、hls.js 集成都是现成的；我们只写「拿地址 → 喂给它」和错误展示。
iPhone 全屏走 `webkitEnterFullscreen`（系统播放器），这一点库已处理。

### 服务端

| 路由 | 做什么 |
|---|---|
| `GET /api/player/page?src=xifan\|girigiri&id&ep` | 渲染新页（一份模板，两个源） |
| `GET /api/player/playlist?src&id&ep` | 转调各自 resolve，输出统一结构 |
| `GET /api/player/stream?u` | `stream.ts` 原样：白名单扩到 girigiri CDN；按域名决定单连接透传 / 12 路 |
| `GET /api/player/hls?u` | 拉 m3u8，把分片地址改写成 `/api/player/stream?u=` |

## 三、决定服务端形态的唯一未知：出口单连接能跑多快

devlog 08-21 实测「VPS → 手机单连接 2.2Mbps < 码率 2.67」，这是预转 HLS 存在的全部理由。
数据是一个多月前在一条链路上测的；**新页动手前先在你的 iPhone 上重测**。

**阶段 0（先做）**：一张 `/api/player/probe` 测速页，手机上打开：`<video>` 单连接播代理 mp4 三分钟，
每 2 秒把 `buffered` 增量打回服务端终端；同时报 `Hls.isSupported()` / `ManagedMediaSource` 有无。

```text
结果 ≥ 4Mbps 持续三分钟且最慢段 ≥ 3Mbps ──▶ 方案 A：纯 mp4 透传，服务端只剩 stream + hls 改写
结果 < 3Mbps ───────────────────────────▶ 方案 B：出口也要多连接
                                          hls.js 自定义 loader 并发预取 N 片（桌面端 07-30 已有同款）
                                          + 服务端 ffmpeg -c copy 切 fMP4（不转码、不分档、不分区）
                                          iOS Chrome 没有 MSE 才退到 sd 转码档
```

方案 B 也比现在小得多：没有 sd 档、没有分区补洞、没有名额队列。

### 阶段 0 结果（2026-09-16，iPhone Chrome，线路二 play.xfvod.pro，经 VPS 代理）

| 测试 | 结果 |
|---|---|
| `<video>` 真播 180s | 播满 178s，中途 0 次 waiting；buffered 领先量一路涨到 100s+；服务端送出 5.0Mbps |
| fetch 单连接 30s × 2 | **4.89 / 4.76 Mbps**，ttfb 0.6~0.7s |
| fetch 4 路并发 30s | 每路 1.23Mbps，合计 4.94Mbps —— **多连接零收益** |

结论：**方案 A**。08-21 的「出口单连接 2.2Mbps」在这条链路上不成立；5Mbps 这个顶是 VPS → 源站那一段
（`play.xfvod.pro` 单连接 4.5Mbps、多路不涨，见 stream.ts 注释），出口不是瓶颈。多连接 / HLS 切片 / 转码
对出口都没有意义，服务端只保留 stream 透传 + m3u8 改写。

顺带确认：iOS Chrome 能直接播 `/api/player/stream` 的 mp4，Range 重连几十次都正常——旧页「direct play failed code=4」
是直连源站那条路的问题，不是 mp4 本身。

## 四、从旧页带走的「已验证的坑」

传输层（`stream.ts`，保留）
- `pan.wo.cn` 见 Origin 头就 403 → 视频字节只能服务端拉，前端永远不 fetch 源站
- `play.xfvod.pro` 必须去掉 `:8088` 用 443（resolve.ts 已做）；该域名单连接透传，12 路反而更慢
- Chromium/WebKit 开 mp4 先探文件尾找 moov：尾部小 Range 直连透传，绝不顶掉正在跑的会话
- 冷 seek 起播闸门 2MiB / 最多 6s；每个 worker 独立 `Agent({connections:1})`

播放页
- `Referrer-Policy: no-referrer`（页面头 + meta）；`<video>` 不加 `crossorigin`
- CSP：不能写内联 `style=`，状态切换只用 classList；脚本要 nonce；hls.js / 监控 SDK 自托管
- 首播 vs 重缓冲**必须分开**（AGENTS.md）：boot 只 `src/load` 保持暂停，等用户手势；首次 `playing` 不算卡顿
- 缓冲提示先等 1.2s 宽限；触屏上**不降速静音预热、不回锚点**（实测饿死播放 / 进度倒退）
- 断网：不换线、不周期探测；只记 源/线路/集/时间点，`online` 后同线路恢复一次
- 换线/换集：先销毁播放器 → detach → abort 请求 → 再起新源；换集直接整页跳转最省事
- bfcache `pageshow.persisted` → reload；`first.source` 不能写死 1
- iOS Chrome：`innerHeight` 比实际绘制区矮 190px，布局按 `100lvh`；固定元素别用 `env()`；系统全屏里看不到我们的 DOM 浮层
- 浏览器原生黑色 loading 转圈藏在 UA shadow DOM，只能用不透明浮层盖
- 诊断日志走 `sendBeacon` 回服务端 stdout，不留浏览器控制台；hls.js 零重试，重试预算全站只有一份

## 五、步骤

1. 阶段 0 测速页（半天）→ 你在 iPhone 上跑一次 → 定 A / B
2. 统一解析输出 + `/api/player/*` 四条路由（不碰旧路由）
3. 新页 + ArtPlayer，先只接稀饭线路二，iPhone 上完整看完一集
4. 接线路一（12 路）、girigiri（m3u8 改写）
5. 「继续看」入口切到新页；旧 `play-page` 保留一个版本周期，Sentry 干净后删

## 六、不做

直连、探测、救援、iframe；慢源名额；预转分档 / 分区；多人带宽；Electron 端。
