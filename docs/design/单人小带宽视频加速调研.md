# 单人小带宽视频加速调研

2026-10-06｜开发交接建议，不是实施或播放验收报告。本次复审仅修改本文：补入“保持源分辨率、至少真实 1080p、观感无明显损失”的硬约束；不修改 011、应用代码或部署配置，不介入正在进行的 bug 修复。

## 结论

**优先保留现有成熟播放器，把主要加速从“播放时现场补数据”移到“观看前准备媒体”。推荐组合：ArtPlayer + 原生 video／hls.js，aria2／HLS 下载工具，FFmpeg，Nginx 静态供片。**

这不是证明过的全局最优算法，而是在“单人、约 6M、弱服务器、少自研、源站波动”约束下，推荐优先验证的工程方案。本轮核对 GitHub 和官方文档，没有测试你的实际服务器、源站或手机。

- 已准备好的片：摆脱观看时的源站波动，争取快速起播、快速拖动、整集无重缓冲。
- 没准备好的片：保留即时播放能力，但它仍受源站吞吐影响。提前准备不等于要求每次点击后坐等整集下载；应尽量在用户观看前完成，例如按用户选择准备接下来的一集。
- **若同时要求陌生冷片立即播放、任意跳转、原画不降质、源站任意变慢仍零卡顿，现有约束之间存在冲突。** 要改善必须引入提前量、更好的供片链路，或客户端下载；降低码率仅在下述画质门槛通过后才是可选项，不能拿可见画质损失换取流畅。
- **画质优先级高于压缩率：保持源分辨率且至少真实 1080p，只发布观感无明显损失的候选；不合格就保留原片，禁止以模糊低档兜底。**
- 不建议又换一遍播放器、恢复旧多级回退，或把缓存命中时的表现当成冷片性能。

## 6M 到底够不够

先按 **6 Mbps** 分析：理论上限 0.75 MB/s，即约 0.715 MiB/s；若实际是 6 MB/s，则约 48 Mbps，是完全不同的预算。还需确认它是出站、入站、双向共享限额，还是测速结果。

要分三段看：源站→服务器、服务器→手机、手机解码显示。单人只消除了其他观众竞争，没有消除源站限速、线路慢段、视频峰值或解码问题。

以下是计算示例，不是本项目实测，假定 24 分钟、总码率包含音频、无协议开销且吞吐稳定：

| 总平均码率 | 一集体积 | 6 Mbps 下载整集理论时间 | 判断 |
|---|---:|---:|---|
| 2 Mbps | 360 MB | 8 分钟 | 有较大带宽余量，仍要检查慢段和峰值 |
| 4 Mbps | 720 MB | 16 分钟 | 平均可供给，余量较少 |
| 8 Mbps | 1440 MB | 32 分钟 | 6 Mbps 出口低于消耗；只缓存到服务器仍未解决出口 |

以实际有效吞吐 C、媒体码率 R 近似，连续播放时缓冲增长率是 C/R−1。C=6、R=4 时，看 5 分钟只多攒约 2.5 分钟，不是后面 20 分钟全已就绪。可变码率还要看目标位置后的数据量，不只看整集平均值。

**服务器完整缓存解决的是上游不稳定，不是下游带宽不足。** 出口不足时，仅可使用已通过画质验收的压缩版本；若合格版本仍喂不饱，则改善出口、增加客户端提前量或提前下载到观看设备，保留画质门槛。浏览器多攒一小段只能抵抗有限慢段，不是无限保险。

## 第一层是不是等同于源站观看

媒体字节、编码、请求地址和网络路径都相同时，可以近似理解为同一份视频；但“复制 URL 到自己网页”未必有相同体验：请求头、签名有效期、IP 绑定、Range、跨域限制、浏览器解码支持及源站的线路选择都可能不同。

若媒体改经你的服务器，还多了一条服务器出口瓶颈。第一层的正确目标是**标准播放、尽量少干预**，不是假设“自己播放器一定比源站快”。跨域 iframe 也不能当成可被自己控制和加速的 video。

## 成熟组件怎样选

下表的能力来自链接中的官方资料；“本项目选择”是本次建议，不是厂商性能保证。没有以星数代替兼容性或本机验证。

| 组件 | 已有能力 | 本项目选择与边界 |
|---|---|---|
| [ArtPlayer](https://github.com/zhw2590582/ArtPlayer) | HTML5 播放器 UI 与扩展集成 | 保留已有 UI，避免无收益替换；它不是下载缓存服务器 |
| [hls.js](https://github.com/video-dev/hls.js) | HLS 播放、缓冲、清晰度切换和事件 | HLS 路径继续使用；MP4 直接走 video。兼容设备也可用原生 HLS，按实际功能检测决定 |
| [Shaka Player](https://github.com/shaka-project/shaka-player) | DASH/HLS 播放与自适应 | 后续真有 DASH 等需求再选；现阶段替换成本高于已证明收益。不要与 hls.js 同时管理同一 video |
| [Video.js VHS](https://github.com/videojs/http-streaming) | Video.js 的 HLS/DASH 引擎 | 成熟替代组合，而非叠加层；不因“更有名”就重写现有交互 |
| [aria2](https://github.com/aria2/aria2) | HTTP 下载、多连接、续传、RPC | 用于 MP4 提前下载；不是现成的任意 seek HTTP 供片服务。连接数从低值试起，测到收益才增加 |
| [N_m3u8DL-RE](https://github.com/nilaoda/N_m3u8DL-RE) | HLS/DASH 等流下载，分片与轨道处理 | HLS 提前获取的候选；用具体源样本验登录请求、清单、时间戳和错误处理，不直接照搬默认并发/重试 |
| [FFmpeg](https://github.com/FFmpeg/FFmpeg) | 探测、重封装、转码、HLS 输出 | 处理完整本地文件的 faststart；可离线试编码，只发布通过画质门槛的版本。重封装不降低视频编码码率 |
| [Nginx](https://github.com/nginx/nginx) | 成熟 HTTP 供片与代理缓存 | 完整媒体由静态文件路径供给，应用留在鉴权和调度侧；减少自写二进制流逻辑 |
| [Nginx slice](https://nginx.org/en/docs/http/ngx_http_slice_module.html) | 把大响应分成 Range 子请求并缓存 | 适合按需复用 MP4 区间；不是主动整集下载器，也不自动提供 seek 优先调度。模块非默认编译，官方列出后台缓存更新限制 |
| [nginx-vod-module](https://github.com/kaltura/nginx-vod-module) | MP4 动态封装成 HLS/DASH，支持本地及远程 Range | 真需要大量动态封装时再考虑；冷段仍依赖上游，且多一份模块部署维护。仓库标注 AGPLv3，接入前核对采用方式 |
| [Shaka Packager](https://github.com/shaka-project/shaka-packager) | HLS/DASH 打包 | 输入已有合适编码时有用；不是用来把高码率自动压低。当前只需 MP4 时不额外引入 |
| [Jellyfin](https://github.com/jellyfin/jellyfin) | 完整媒体服务器和客户端生态 | 愿意迁入独立媒体库才值得整体采用；仅为现有网页提速而接入整套系统，增加业务和运维边界。远程源适配仍需处理 |
| [P2P Media Loader](https://github.com/Novage/p2p-media-loader) | 浏览器之间分享视频分片 | 单人没有同片观看伙伴，缺少有意义的加速来源，排除 |

成熟播放器支持自适应，不代表单档源凭空出现低码率档；多档媒体必须先存在。Jellyfin 的客户端能力与码率约束驱动服务端选择的思路值得借鉴，但不是照搬其完整应用。[Jellyfin 官方转码说明](https://jellyfin.org/docs/general/post-install/transcoding/)

## 推荐架构与明确取舍

```text
已有源站解析和鉴权
  → 提前获取接下来要看的媒体
  → 私有临时目录
  → 完整性与媒体校验
  → 无重编码封装整理／可选离线试编码
  → 分辨率与画质准入检查（不合格保留原片）
  → 原子发布为可用媒体
  → 应用鉴权 → Nginx 供片 → 现有播放器
```

这条是“已准备媒体”的主路径；未命中时沿用当前即时播放路径，不在前端新增直连→救援→转码→iframe 的自动回退链。

### 先把完整本地媒体播好

先拿一集已完整获取的真实媒体，经过相同 HTTPS、鉴权和手机网络，比较 Nginx 静态供片与当前链路。若静态文件都卡，先处理出口、媒体码率或设备解码；继续优化源站预抓没有针对性。

对于兼容的 MP4，优先原生播放。尾部 moov 用 FFmpeg 对本地完整文件做 faststart，避免在这条热路径维护虚拟文件偏移转换。该操作需要第二遍整理，计入准备耗时；不是网络拉流时的无成本开关。[FFmpeg 官方格式文档](https://ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv)

下载工具的完成状态、长度/分片集合、媒体时长、音视频轨道、首中尾可解码性共同决定“就绪”。预分配文件的长度不代表字节全到；孤立的本地 SHA256 也不证明内容与源站一致，有上游可信摘要时再做一致性比较。

**未完成文件不交给普通 Nginx 静态服务。** 多连接下载会留下空洞，文件大小可能提前到位；静态服务不会替你等待空洞被填好。若继续追求任意位置的边下边播，就仍然需要一个经过验证的区间调度/读取层，aria2 并没有替你完成这一层。这正是本方案优先绕开的复杂度。

### 用提前量而不是大内存

优先准备用户明确要看的下一集或小范围待看队列，不抓全站。当前播放拥有资源优先权；入出站分别限速时可并行，共享瓶颈时下一集应让位。控制下载、校验、转码的总资源预算，不只统计下载线程。

完整 MP4 经静态供片即可满足许多场景，不强制转 HLS。若需要节省流量，先按下节的质量约束离线试编码；只有画质通过才可发布。确有多个合格版本并需要自动调档时，再生成时间线、关键帧对齐的 HLS；所有档位保持源分辨率且至少 1080p，全部通过相同画质门槛。带宽低于最低合格档时等待或改善链路，不隐藏切到模糊档。只有一个合格版本时，不为 ABR 人造一个劣质低档。

弱服务器转码速度未知，先测准备耗时；优先在空闲时处理，或在更合适的设备准备后上传，别让实时重编成为每次点击的前置步骤。已有历史压制结果也要按今天的样本复验。

### 保留一层小而明确的业务适配

成熟组件能替代下载、封装和供片，但没有本轮已核实的单一项目能直接包办稀饭/Girigiri 登录、短效签名、选集、鉴权和你的 UI。

适配层只负责：媒体任务身份、凭证请求、状态、取消、配额、发布和回收。

- 媒体身份含源、集、线路、版本及权限范围；不要仅凭去掉 query 的 URL 合并缓存。临时签名改变和内容改变是两件事；跨地址续传前核对版本/长度/校验信息，证据不足则重新获取，避免混片。
- 缓存不绕过本站权限；本地媒体目录保持私有，应用鉴权后交给 Nginx internal 路径。原始第三方凭证不进入公开 URL、日志或报告。[Nginx internal 文档](https://nginx.org/en/docs/http/ngx_http_core_module.html#internal)
- 401/403/429/5xx 停止并显示具体原因，不让下载器、播放器、应用层分别重试；传输中断若要续传，预算只有一份。aria2 默认会尝试多次，HLS 下载工具也有分片重试，接入前必须显式配置并用失败夹具计数。[aria2 参数](https://aria2.github.io/manual/en/html/aria2c.html) / [HLS 下载参数](https://github.com/nilaoda/N_m3u8DL-RE)
- 使用任务取消句柄、owner 和代次；用户换集、撤销准备时释放旧任务，不只忽略晚到结果。
- 容量预算包含原片、整理临时副本、转码档、下载中空间。正在供片的资源有占用保护；满盘时明确失败，不删当前播放文件抢救预取。

## 画质是硬门槛而不是可牺牲的参数

**目标：在保持源画面尺寸、至少真实 1080p、与源站选定画质相比无可辨认劣化的条件下，寻找已测试候选中码率最低的版本。不是先定一个码率上限，再把画面压到能塞进去。** “观感等同”是约定设备与观看条件下的验收结果，不是对所有人、所有显示器的数学保证。

### 必须保留什么

- 对照基准是同一集、同一版本、源站实际选定的高清媒体，不拿源站较低档当基准。保存源文件身份及媒体参数，避免前后比较的内容不同。
- 保持原始宽高、显示比例和有效画面；1080p 源保持 1080p，更高分辨率源也不降到 1080p。低于 1080p 的源须另找合格片源或明确标记不满足要求，不插值放大后冒充真实 1080p。非 16:9 内容按有效画面检查，不靠补黑边凑尺寸。
- 保持帧率和时间线，不降帧、不裁切；保留正确的色彩范围、色彩元数据和 HDR/SDR 呈现。默认不减位深、不降低色度采样，不用模糊、去颗粒、磨皮或锐化掩盖压缩损伤；音频优先复制，不为视频省码率偷偷牺牲声音。
- 默认优先原码流缓存/重封装。FFmpeg streamcopy 不解码再编码，避免新增编码损失，但通常也没有显著的视频码率收益。[FFmpeg streamcopy 文档](https://ffmpeg.org/ffmpeg.html#Streamcopy)

### 怎样寻找更低码率而不靠猜参数

1. **质量优先搜索，而非全站固定参数。** 先在细线/发丝、字幕、平涂渐变、暗部、颗粒、快速运动、镜头摇移、复杂特效等片段试编码；由较高质量向更低码率逐级试探，出现劣化就退回。样本只用于筛选参数，最终整集仍要质量检查。记录节省比例和编码成本，只保留有实际收益的候选。
2. **候选编码器是工具，不是画质承诺。** 先测兼容性优先的 H.264；HEVC/AV1 只有在目标设备实际播放、硬件解码/功耗、封装支持及准备耗时都合格时再用。编码器更先进不代表每份已压缩源都能等质大幅缩小；兼容不通过时回原片，不临时补一条实时转码链。
3. **CRF 不等于“人眼无损认证”。** CRF、preset 与内容共同影响码率/失真，不同编码器的 CRF 数字也不能直接横比。VBV/maxrate 限制可能迫使复杂场景牺牲质量；加了峰值约束后必须重新验画质。不预设“1.2 Mbps”“CRF 23”或固定压缩百分比适用于所有番。[x265 码率控制说明](https://x265.readthedocs.io/en/master/cli.html#quality-rate-control-and-rate-distortion-options)
4. **流畅与画质分别过关。** 同一清晰度下更低的平均码率未必消除短时峰值；画质合格后仍用实际分片大小/局部码率和完整播放验吞吐。如果满足带宽的候选都出现可见劣化，判该片压缩路线不通过，保留原片，不继续降低质量追求达标。

### 画质准入与失败处理

采用“自动指标筛查 + 人眼对照”的两道门，不以 1080p 标签或单个平均分放行。

- 用对齐后的同源帧计算 VMAF，并辅以 SSIM；渐变色带可加 CAMBI 检查。记录工具/模型版本、颜色处理、逐帧或分段结果、低分位和最差连续片段，不只记录全片均分。检测输入不做掩盖差异的缩放、锐化或去噪。[Netflix VMAF 与相关指标](https://github.com/Netflix/vmaf)
- **没有一个通用的 VMAF/SSIM 分数能保证“用户看不出来”。** 初期由用户认可的原片/候选 A/B 样本校准数值门槛并锁定；尚未校准时不自动上线有损压缩版。后续自动筛查发现异常时回退原片，数值通过但人眼发现问题也判失败。
- 隐藏版本标签并随机顺序，在同屏同尺寸、同亮度、同步时间下比较原片与候选。至少覆盖实际 iPhone 和 1080p 或更高显示器上的正常全屏观看；正常速度观察运动，再检查关键帧局部。不能只用手机缩小画面证明桌面也无差别。
- 不接受可辨认的细线/字幕发糊、纹理或颗粒消失、色带、块状噪声、蚊噪、运动拖影或颜色变化。任一审查片段出现可重复识别的新增劣化就退回更高质量候选/原片；差异定位可用放大图，但以预先约定的正常观看条件作为观感门槛。
- 每个发布候选保留源身份、完整编码参数、实际宽高/帧率/颜色、总码率与局部峰值、指标报告、人眼审核结论、目标设备播放结果。小样本“未发现差异”只支持该验收范围，不宣称绝对无损；无充分证据时供原片。

这条路线追求的是**视觉等同下的码率收益**。如果用户要求逐像素完全一致，则应保留原码流或使用真正无损编码；后者不保证文件比已有有损源小。即使允许人眼难辨的损失，也可能几乎没有剩余压缩空间，尤其是源站已经高度压缩的内容。

## Nginx slice 什么时候反而更合适

如果用户常常随机点陌生视频、不接受准备等待，而且源站大多数时间快、稳定支持 Range，按需 slice 缓存是更节省磁盘和首播等待的候选。HLS 则以真实分片对象缓存，而不是把所有请求当 MP4 byte slice。

代价是：冷 seek 仍要等源站；请求没到过的位置不会自动变热。播放器不开请求时，缓存也不等于独立后台下载器。它适合“尽力改善即时播放”，不是“切断源站后任意位置都可播”的保障。

若要迁移在线缓存，做独立对照验证后再替换，不在当前修复中叠加第二套下载器、slice 和旧缓存同时抓同一文件。不要把未来路线直接当成删除当前 disk 工作的理由。

## 为什么以前已经要求顺畅却还没成功

当前 [011 接手记录](../ideas/011-在线观看.md) 明确区分了完成与待验：统一 ArtPlayer 已采用；旧预转、多级回退已撤；10 月 6 日磁盘调度仍在修改，整集播放、冷 seek、取消与错误预算仍列为待验。本文只读取文档，不据此宣称某条当前源码已证实有 bug。

可解释的工程原因是：

1. 成熟的是播放器；服务端动态区间缓存、虚拟 faststart、读写并行和预取竞争仍有自研成本。
2. 历史“178 秒不卡”或“起播 3～5 秒”是有限样本，不覆盖整集和任意拖动；源站和网络还会变化。
3. 缓冲提示/重挂地址只能处理状态，不能补上尚未传到的数据。
4. 调整封装可以改善索引与请求方式，视频重编码才可能显著降低视频编码码率；解决入口问题也不自动解决出口问题。

所以不是“B站效果没人会做”，而是**标准点播里已准备好的媒体**，被换成了**第三方随取随用、尚未准备好的媒体**，体验目标却仍按前者验收。这里借鉴的是成熟点播的准备/供片分工，不宣称掌握 B站内部实现。

## 开发者怎样验收而不是继续盲调

先记录 6M 的单位/方向、实际设备和浏览器版本、源格式/编码/总码率与峰值、可用磁盘、CPU、签名有效期、Range 响应。只在用户选定样本做有界测试，不运行源站恢复轮询。

**建议目标，不是已测结果：**在约定有效网络与已准备媒体集合内，点击播放到画面持续推进的 P95 ≤2 秒，提交 seek 到目标画面持续推进的 P95 ≤2 秒，每集首次起播后非用户操作重缓冲次数为 0。未达标记录实值和原因，不擅自放宽。至少每种格式 20 次独立起播、20 次分布于片头/中/尾及来回跳转的 seek；P95 同时附原始样本和最大值。

| 场景 | 必须得到的证据 |
|---|---|
| 已准备 MP4，头部/尾部 moov 原片 | iPhone Chrome 与桌面各完整一集；记录起播、重缓冲、丢帧、Range 与首字节 |
| 压缩画质 | 保持源宽高且至少真实 1080p；逐段指标及盲测通过，细线/字幕/渐变/暗部/运动无可辨认新增劣化；不合格回原片 |
| 已准备 HLS | 清单、初始化段、音视频轨道/密钥引用完备；原生 HLS 与 hls.js 各回归；不拿 MP4 结果代替 |
| 热 seek | 片头/中/尾、连续前后拖动；准确恢复时间、无重复播放/倒退、旧请求退出 |
| 冷起播与冷 seek | 单独标冷缓存，记录准备等待、吞吐和失败；绝不混进热缓存成绩 |
| 上游不可达 | 仅在隔离测试中阻断媒体上游，保留用户到本站链路及本站鉴权；已就绪媒体仍完成播放和随机 seek |
| 出口不足 | 用可重复限速，仅允许已通过画质门槛的版本；不足则等待，不降分辨率或偷切模糊档；验证“服务器有全片”没有被误当出口充足 |
| 错误和版本变化 | 401/403/429/503、断流、签名更换、Range 回 200/416、同集内容更换；统计每层请求数和缓存身份 |
| 生命周期 | 暂停、后台、断网恢复、换集、取消、进程重启、满盘；无空洞、截断、串片及旧任务占资源 |
| 下一集准备 | 对比启用/停用时当前集完整播放；同时记 CPU/磁盘/入出速率，预取不得让当前集变差 |

日志落服务端终端，带脱敏请求/任务 ID；起播、用户 seek 等待、自然重缓冲分别计时。画面推进/呈现才是恢复证据，不把 seeked 或首个字节当播放恢复。人工点击与自动采样一起保存。

先做“完整本地文件→静态供片”的小基准；通过后接准备队列；需要进一步节省码率时才加入质量受约束的离线试编码；画质和播放两道验收都通过才替换原片。每一步只改变一个因素并留可切回路径。调研没有替代真实兼容性验收，但它把需要验证的范围缩到集成与边界，而不是重新发明下载器和媒体服务。

## Gemini's response

以下为补充画质硬约束之前的两轮讨论，本次修订没有再次向 Gemini 提问；其中“降码率/多档”的建议一律受本文新的画质准入规则约束，不视为它已复核本次规则。

在用户指定的 Gemini 账号完成两轮问答。[完整对话](https://gemini.google.com/u/6/app/a3ece98b93c91b8e?pageId=none)。第一轮只发用户需求，第二轮发本报告候选方向及公开资料供反方审查；没有上传本地代码、011 或凭证。

**第一轮意见：**ArtPlayer + hls.js 超大前向缓冲，配合 Nginx 缓存；同时提到签名过期、磁盘容量和 MP4 要另行处理。但它把浏览器缓冲说成可以无限增大，给出了没有测量依据的固定起播时间、零毫秒 seek，并错误推算预下载量。

**第二轮意见：**收到反证后，Gemini 承认这些问题，支持“异步获取完整媒体→FFmpeg 整理/必要转码→Nginx 分发”，强调准备时间、签名/IP 条件、空间和冷 seek 的代价；它还建议冷片使用 slice/代理缓存、热片静态分发、准备下一集。

**采用：**将不稳定的源站获取移出热片播放关键路径；冷/热分开；用成熟供片与媒体工具；充分计算准备时间和存储成本。

**不采用或修正：**

- 浏览器配额存在，但不是所有平台统一 150 MB；超配额也不必然导致整个播放器崩溃，库可能释放缓冲恢复。把 hls.js 参数调到 500 MB 不代表系统允许保存那么多媒体。依据是配额及回收机制，而不是某个历史固定数字。[Chrome 官方说明](https://developer.chrome.com/blog/quotaexceedederror) / [WebKit MMS 说明](https://webkit.org/blog/14735/webkit-features-in-safari-17-1/)
- “所有 seek 都清空缓冲”“faststart 前几 KB 就一定开播”“转码必定 15～30 分钟”缺少适用于本机的依据，不进入验收承诺；已缓冲 seek 可以避免重新下载。[hls.js 功能说明](https://github.com/video-dev/hls.js)
- 未证明两个源都存在 IP 绑定，更未证明必须常驻无头浏览器。复用现有源适配层，按真实响应确认请求条件，不新造浏览器抓取服务。
- 短效地址不等于必须同时下载全部切片。任务真正开始时再解析地址，保持有界调度；签名有效期短到不够完成时，应明确失败/受控刷新并校验内容身份，而非请求风暴。
- 不同时让前台 slice 与后台独立下载器争抢同一冷集；如将来融合，先证明请求复用和统一预算。下一集也不是不顾当前片状态立刻占满资源。
- “文件存在”不足以判就绪；按完整性验证后的发布状态判断。“刷新页面”不是无缝切换。
- “唯一最优解”过强。该方案最契合优先流畅和减少自研；优先随机即时观看的人，可能更适合按需缓存或更好的供片出口。

外部 AI 的一致意见不作为性能证据。最终推荐依据仍是组件能力、明确的物理边界和上面的可复现验收。
